# U61: where the tokens went

The user pays per token. A turn's footer already gave its model, tokens and cost. It did not say which part of the request the money went to. Now the footer's usage line opens a breakdown of the turn by part, with a Session tab beside it, and `gcode usage` prints the same numbers. The contract is the U61 row in the table at the end of `docs/plan-u19-on.md`.

## What the user sees

- **The usage line.** On a finished turn whose prompt the engine has numbered, the footer's model, tokens and cost are one button with a chevron. It opens a card under the footer. The footer's text is unchanged.
- **This turn.** One row per part that has tokens. Each row has the label, the tokens, the share, a bar, and the cost in baht with USD beside it. The biggest driver is named above the rows ("Tool definitions are 60% of the cost") and its row is bold with an amber bar. Under the rows: the model calls, the tokens and the total, then how the input billed ("Cache read 5.2k · write 5.5k · uncached 2.9k · output 72"), then what the numbers rest on.
- **Session.** The session's turns and total, the costliest turns (at most 5) with each one's driver, the subagents' count and cost, then the same rows over every request of the session.
- **External agents.** A turn on Cursor or Claude Code shows "Cursor plan, no token data" (or "Claude plan, no token data"), with a cost only when the agent reported one.
- **Keys.** Escape closes the card and puts the keyboard back on the usage line. The tabs and the close button are buttons.

The share is of the cost when the model is priced, and of the tokens when it is not. The subagents' cost counts toward a turn's share, so a turn whose children cost most names "Subagents" as its driver. Baht use `gcode.chat.bahtPerUsd` (33 by default).

## Data shape

`packages/core/src/parts.ts` names it. The webview imports it, so it imports no node module.

- `PARTS` lists the parts in the order a request sends them: `tools`, `system`, `context` (rules, memory, skills), `user` (earlier prompts), `assistant` (earlier replies), `toolResults`, `files` (read this turn), `attachments`, `prompt` (this turn's prompt), then `output`, and `unsplit` for a request logged before this unit. `PART_NAMES` gives each its label and the subject of the driver sentence.
- `PartRun` is `[part, tokens]`: one stretch of a request that one part fills, as estimated. Each model call logs its request as runs, in order, on the `assistant` event's `promptParts`.
- `TokenBasis` is the estimate flag. `provider` means the provider counted the request's input and the parts share that count. `estimated` means the provider reported no input count, so the total is the estimate too, and the card says "Estimated".
- `PartUsage` is a part's `TokenUsage` by bucket (uncached input, cache read, cache write, output) and its cost, null for an unpriced model. `Breakdown` holds `basis`, `requests`, a `PartUsage` for every part, and the total.
- `spend.ts` builds `SessionSpend` from a log: one `TurnSpend` per prompt, either `model` (its `Breakdown`, its children, its cost) or `external` (the plan and any reported cost), plus the session's breakdown, children, total and the seqs of the 5 costliest turns.
- `spend-view.ts` turns those into the strings both the panel and the CLI print: `turnSpendView`, `sessionSpendView` and `spendLines`.

## How a request is split

`requestRuns` (in `breakdown.ts`) walks the request the gateway is about to send, with the log it was built from:

- Each tool definition is `tools`. The system prompt is `system` up to the memory section, which is `context`.
- A user text block that is the session's loaded context is `context`. One that is a prompt from an earlier turn is `user`, and one from this turn (its prompt or a steer) is `prompt`. The block of mentions and attached files is `attachments`, except the rules and skills it carries, which are `context`. An image is `attachments`.
- A tool result is `files` when it is a `read` in this turn, and `toolResults` otherwise. The same file read in an earlier turn is a tool result now, which is why the Session tab calls the part "Files as first read".
- Assistant blocks are `assistant`. Thinking counts only on the Anthropic wire, since Chat Completions drops it.

`requestBreakdown(runs, usage, rates)` is the attribution. It is pure and table-tested.

1. When the provider counted input, the runs share that count in proportion to their estimates, by largest remainder.
2. The cached prefix is the front of the request, so the runs are laid end to end: the first `cacheRead` tokens billed as cache reads, the next `cacheWrite` as cache writes, and the rest as uncached input. A part gets the buckets its stretch overlaps.
3. `output` gets the output tokens. Each part's cost is its buckets at the model's rates.

**Tolerance.** With the provider's count, the parts sum to the request's usage exactly, in every bucket. Their costs sum to the request's cost within 1e-9 USD (floating point). `packages/core/test/breakdown.test.ts` checks both on every table case, on a whole turn, and through `gcode usage` in `packages/engine/test/usage.e2e.test.ts`.

**Provider counts.** The provider counts the request, not its parts. No provider Geno uses returns a per-part count with the call, and asking Anthropic's `count_tokens` once per part would cost a round trip per part. So the total is the provider's and the split is the estimate, and the card says so in one line.

## The tokenizer approximation

`estimateTokens` in `breakdown.ts` is the one approximation, and `TOKENIZER` holds its constants. Text splits the way BPE pre-tokenizers split it. A run of Latin letters costs one token per 8 letters, rounded up. A letter outside Latin and each digit cost one token, since Qwen tokenizes digits one at a time. A run of other symbols costs one per 3. A whitespace run costs one, and a lone space costs nothing. Framing adds 4 per message, 8 per tool call or result, 15 per tool definition, and 190 once when any tool is offered (the chat template's tool instructions). An image counts 1,600 tokens, Anthropic's cap for a full-size image.

It was calibrated on qwen3.8-flash in two ways.

- **The conversation.** Between two requests of one session the system prompt and tools stay the same, so the growth of the provider's count is the conversation added in between. `pnpm tsx packages/engine/test/usage-calibrate.ts` compares that growth with the estimate's over the logs in `~/.g-code/sessions`, with no model call. Over 177 sessions from the last 6 days, 2,569 request pairs and 2.22M tokens, the estimate was 1.014 of the count overall, median 1.002, p10 0.915, p90 1.084.
- **The prefix.** Four direct requests (no tools, 1, 6 and 12 of the agent's tools) separated the system prompt, which the estimate had within 0.3%, from the tool definitions, which it had 10% to 33% short. The per-tool and once-per-request framing above close that gap.

The prefix constants were fitted on the same agent tool set the live check uses. The live check therefore tests the prefix in sample, and the log comparison is the out-of-sample evidence for the rest.

## Live check

`pnpm tsx packages/engine/test/usage-smoke.ts` runs one `gcode agent` turn on Model Studio qwen3.8-flash: read `prices.ts`, then answer in one sentence. It checks that each request's estimate (the sum of its logged runs) lands within 5% of the input the provider reported. `--log <session.jsonl>` checks an earlier run's log without a call.

| Request | Reported | Estimated | Error |
| --- | --- | --- | --- |
| 1 | 4,201 | 4,238 | +0.88% |
| 2 | 4,301 | 4,318 | +0.40% |
| 3 | 4,453 | 4,456 | +0.07% |

It passed, with the largest error 0.88%, for $0.0023. Calibration and the earlier runs brought the unit's spend on Model Studio to about $0.009 of the $0.03 allowed. The key appears in no output.

## CLI and engine

- `gcode usage --session <id> [--json] [--baht-per-usd 33]` prints the session line, the basis, the cache split, the rows, the subagents, the costliest turns, and each turn's rows. `--json` prints the `SessionSpend` with `bahtPerUsd` and `view`: the session's view and each turn's view, the exact strings the panel draws.
- `_gcode/usage { sessionId }` returns the `SessionSpend` for the session the panel shows. `UsageHost` in the extension asks for it when a usage line opens, and the webview builds the views with the user's baht rate.
- The gateway computes the runs from the request it sends, so they hold the system prompt, memory and tools of that call. Logs from before this unit have no runs, and their requests show as "Not split (older log)".

## Deferred

- A rewind's cut turns leave the report, because `readSessionLog` gives the cut view. The money for them was spent, so the session total undercounts after a rewind.
- The calibration covers qwen3.8-flash. Another model's tokenizer may differ by more, and the card's split would shift with it while the total stays the provider's.
- Images count a flat 1,600 tokens each instead of their size.
- The panel's costliest turns do not yet jump to the turn when clicked.
