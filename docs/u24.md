# U24: lanes engine

A lane is a parallel session in its own git worktree. `gcode lane new` makes one, a session whose workspace is the lane can edit and run commands only inside it, and `gcode lane apply` merges its work into the main checkout as changes for review. The brief is the U24 section of `research/competitors-2026-10.md` (sections 3.3, 3.6 and 5). The panel is U25.

## Data shape

`packages/core/src/lanes.ts` names it. Pure logic lives there; `packages/engine/src/lanes.ts` does the git and file work, and `lane-cli.ts` is the command.

- `LaneRecord` is `{ name, path, branch, base: { from, commit }, session, createdAt }`. `name` is a `LaneName`, which `parseLaneName` allows only when it is safe as a folder and a branch name: letters, digits, `.`, `-` and `_`, 48 at most, with no `..` and no `.lock` ending. `path` is the worktree's real path, `branch` is `geno/<name>`, `base.from` is `head` or `main`, and `base.commit` is the commit the lane started from, which is the merge base when it is applied. `session` is the last session that ran in the lane, or null.
- `Lane` adds `status`, which is computed each time and never stored. `clean` means no edits, no untracked files and no commits since the base. `changed` means any of those. `missing` means the worktree folder is gone. `isDisposable(status)` is true for everything except `changed`. Sweep and discard ask only that function.
- `LaneApplyResult` is all or nothing. It is `{ kind: 'clean', changes }`, where each `LaneChange` holds a `FileChange` (the hunks the review flow shows), the text to write (`after`, null for a deletion) and the hash of the main file it applies over. Or it is `{ kind: 'conflicts', conflicts }`, a list of `{ path, reason }`, and then nothing is written.
- `SetupApproval` is `{ repo, commandsHash, commands, approvedAt }`. It lives in `<app home>/lane-setup-approvals.json`, one entry per repository, keyed by the main checkout's real path. A changed command list has a new hash, so Geno asks again.
- `mergeStepOf({ base, ours, theirs })` decides each file before any merge runs. `ours` is the main checkout now, `theirs` is the lane now, and null means absent.

| Case | Step |
| --- | --- |
| main and lane agree, or the lane left the file alone | `same`: nothing to do |
| a binary file on any side | conflict `binary` |
| main still has the base text | `take` the lane's text, or delete |
| both added the file | conflict `added-in-both` |
| the lane deleted a file main changed | conflict `deleted-in-lane` |
| main deleted a file the lane changed | conflict `deleted-in-main` |
| both changed it | `merge`: `git merge-file`. Overlapping changes are conflict `both-changed` |

A symlink or submodule is conflict `special`. Lanes do not apply these yet.

### Path-check denial reasons

`laneCommandDenial(command, cwd, bounds)` reads a lane session's `bash` command before it runs. `bounds` lists every spelling of the lane and the main checkout. macOS's `/var` and `/tmp` are links into `/private`, and a model can write either form.

| Id | Refuses | Example |
| --- | --- | --- |
| `cwd-outside-lane` | a command whose folder is not in the lane | the tool's cwd is the main checkout |
| `cd-outside-lane` | a `cd` or `pushd` out of the lane, or to a folder that only exists at run time | `cd ..`, `cd`, `cd -`, `cd "$(git rev-parse --show-toplevel)"` |
| `git-c-outside-lane` | `git -C` to a folder outside the lane | `git -C ../../.. commit` |
| `git-dir-flag` | `--git-dir`, `--work-tree` or `core.worktree`, with any value | `git --git-dir=/repo/.git log` |
| `git-env-redirect` | an assignment to `GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE`, `GIT_COMMON_DIR` or a similar variable | `GIT_DIR=/repo/.git git log` |
| `path-in-main` | a word that resolves into the main checkout but not into the lane | `echo x > ../../../a.ts`, `/repo/a.ts`, `--outDir=../../../dist` |

The check splits the command the way `sh` does in the cases that matter. Quotes and backslashes join words. `; && || | & ( )`, newlines and backquotes separate commands. A `cd` inside a subshell, a pipeline or the background does not last, so the check keeps every folder the command could be in and tests each word against all of them. A word with `$`, a backquote or a glob cannot be known before the command runs. In a `cd` or `git -C` target, such a word is refused. In any other word, it is skipped.

## Commands

```
gcode lane new <name> [--from head|main] [--approve-setup] [--workspace <dir>]
gcode lane list [--json] [--workspace <dir>]
gcode lane apply <name> [--dry-run] [--workspace <dir>]
gcode lane discard <name> [--discard-changes] [--workspace <dir>]
gcode lane sweep [--workspace <dir>]
```

- **new.** The command refuses a 26th lane and suggests `gcode lane sweep`. The cap is `LANE_CAP`, 25, Cursor's default. It adds `/.geno/` to `.git/info/exclude` once. That file is never committed, so the user's `.gitignore` stays untouched. It runs `git worktree add -b geno/<name> .geno/worktrees/<name> <base>`, where `--from main` uses `main`, or `master` when there is no `main`. It writes the record to `.git/geno/lanes/<name>.json`. Then it does three things:
  - It copies each file listed in `.worktreeinclude` that git ignores, such as `.env`. A tracked file is already in the lane and is not copied, as in Claude Code.
  - It clones every `node_modules` folder of the main checkout, one for each tracked `package.json`, with `cp -c -R`. If a clone fails, the command reports it and does not fall back to a full copy.
  - It runs the setup commands, after an approval (see below).
- **list.** Prints each lane with its status, branch, base, bound session and path.
- **apply.** Builds the lane's working tree as a tree object in a scratch index. Uncommitted and untracked files are included, and the lane's own index is untouched. It diffs that tree against the lane's base and runs `mergeStepOf` and `git merge-file` per file against the main checkout's current files. If the result is clean, it writes the files and lists them with hunk counts. Before it writes anything, it checks that no main file changed since the merge read it. On conflicts it lists them, writes nothing, and exits 1. `--dry-run` reports without writing.
- **discard.** A `changed` lane is refused unless the user passes `--discard-changes`. Discard removes the worktree, its `geno/<name>` branch and the record.
- **sweep.** Removes every `clean` or `missing` lane and lists the `changed` ones it kept. It never removes a changed lane.

## Setup

The setup commands come from `laneSetup` in `.gcode.json` (a string or a list). If that is absent, they come from `setup-worktree-unix` or `setup-worktree` in `.cursor/worktrees.json`, so existing Cursor setups work. The commands run in the lane, outside the sandbox, because installing needs the network that the sandbox denies. They get the child environment plus `ROOT_WORKTREE_PATH`, as in Cursor. The first time a repository's list is seen, `lane new` asks on the terminal. `--approve-setup` gives the same yes. A non-interactive run without the flag skips setup and says how to approve it.

## Isolation

Three layers keep a lane session out of the main checkout:

1. **Binding.** `runAgent` asks `laneAt(workspace)` whether the session's workspace is inside a lane. The workspace's git top level must be `<main>/.geno/worktrees/<name>` and have a record. If it is, the record gets the session id, and the session runs with that lane's bounds. Nothing has to opt in. A serve session whose cwd is a lane gets the same binding through the same path.
2. **Edits.** The workspace is the lane, so `resolveWritable` already refuses an edit to `../../../a.ts` or to an absolute path in the main checkout, after following symlinks.
3. **Commands.** The `bash` tool runs `laneCommandDenial` before the approval rules. Behind it, the sandbox lets a lane session write only to the lane, the temp folder, and the parts of the shared `.git` that the lane's own git commands write: its `worktrees/<name>` folder, `objects`, and `refs/heads/geno` with its logs. So a path built at run time still cannot write into the main checkout, and `git commit` still works in the lane. The main checkout's index and `HEAD` are not writable.

The network allowlist is the same for every lane. sandbox-runtime keeps one configuration and one proxy per process (`docs/plan-u19-on.md`), so per-lane network rules are not possible in one engine.

## Copy-on-write measurement

I measured on this repository's own pnpm 11.3.0 install, on the macOS APFS data volume. The install is four `node_modules` folders. The root one is 491 MB with 1,311 symlinks, and every symlink is relative, such as `vitest -> .pnpm/vitest@5.0.3_…/node_modules/vitest` and `@g-code/core -> ../../../core`. I cloned the four folders into a scratch copy of the repository's layout. Each number below is from one run, so expect some noise.

| Measure | Result |
| --- | --- |
| `cp -c -R` of all four folders | 6.9 s |
| `cp -c -R` of the root folder | 4.8 s |
| plain `cp -R` of the root folder | 13.5 s |
| dangling symlinks in the clone | none |
| `tsc --noEmit -p packages/engine` run from the clone | exit 0, 2.2 s |
| `import('vitest/config')` from the clone | resolves |

The clone works with pnpm's layout. The links are relative, so they resolve inside the clone, and workspace links such as `@g-code/core` point at the lane's own package. The clone is about 3 times faster than a copy. Its limit is the number of files, not their bytes. I infer that it uses almost no disk, because the volume's free space did not drop by anything near 491 MB. Other writes on the machine moved `df` by more than the clone did, so I have no exact number. `lanes.e2e.test.ts` checks a pnpm-style relative link through `gcode lane new` on macOS. Other platforms report `unsupported` and leave dependencies to setup.

## Check

- `packages/core/test/lanes.test.ts` covers lane names, `isDisposable`, each `mergeStepOf` row, the shell splitter, every denial id with its escapes (`git -C`, `cd ..`, an absolute path, an aliased absolute path, `GIT_DIR`, `--git-dir`, `core.worktree`, a subshell or pipeline `cd`, a backquote), and commands that must still run.
- `packages/engine/test/lanes.e2e.test.ts` runs against temp repositories:
  - Two lanes edit the same line. The first applies cleanly (two files, one of them new). The second reports one `both-changed` conflict and leaves the main file as the first left it. A third lane, which committed a change to another line, merges 3-way.
  - The main checkout's `git status` shows only the applied files, `.git/info/exclude` holds `/.geno/`, and no commit was made.
  - Sweep removes only the clean lane and keeps lanes with edits, commits or untracked files. Discard refuses a changed lane without `--discard-changes`.
  - The cap refuses lane 26.
  - `--from main` works while the main checkout is on another branch.
  - `.worktreeinclude`, the copy-on-write clone, and setup: not run without approval, run with `--approve-setup`, run again without asking, and asked again after the commands change. A second test reads setup from `.cursor/worktrees.json`.
  - A session in a lane, run through `gcode agent` with a fake model in Ask mode with every prompt approved, so only the lane checks and the sandbox stand in the way. Two edits that escape are refused. Six commands that escape are refused with their denial reasons. A symlink built at run time passes the text check, and the sandbox refuses the write. Then the main checkout's file hash, its `git status`, its log and the absent marker files show it untouched. Meanwhile the lane got the edit, a file and a commit, and the lane record names the session.
- `pnpm typecheck && pnpm vitest run --project unit && pnpm build` and `pnpm lint:deps` pass.

## Deferred

- Binary files, symlinks and submodules are reported as conflicts and not applied.
- Apply writes the merged files into the main checkout and prints the hunks. Showing them in a session's review state, with keep and undo per hunk in the panel, is U25's part. `LaneChange.change` is already the `FileChange` that flow takes.
- Sweep runs on demand. Nothing sweeps by itself.
- Lanes share the network allowlist (see Isolation).
- Reads are only partly fenced. The read tools see only the lane, as with any workspace, and `path-in-main` refuses a command that names a main checkout path. The sandbox does not deny reads there, so a path built at run time can read the main checkout. Claude Code's checks allow the same.
