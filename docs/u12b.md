# U12b: MCP in the panel

The chat panel shows the open chat's MCP servers, asks before a workspace server runs, and no longer holds the first prompt while a cold server starts. U12a's engine (`packages/engine/src/mcp/`) does the work; this unit adds the panel, the forwarding of the user's own servers, and the background start.

## In the panel

- **MCP view.** The server action in the Chat view's title (`gcode.chat.mcp`) puts the list in the transcript's place, like the history. Each server shows its name, where it is defined, its state and its tools. The states read Needs your approval, Starting, Ready with the tool count, Failed with the reason, Needs sign-in, and Off. Escape or the back arrow returns to the chat.
- **Trust card.** A server from `.mcp.json` or `.vscode/mcp.json` waits behind a card. For a stdio server it shows the exact command line, shell-quoted as it runs, its working folder, and every env value it sets. For a remote server it shows the URL and the names of the headers it sends; header values are left out, since they are often credentials. Allow approves that definition, and the request carries the hash of the definition the card showed, so the engine refuses an approval of anything else. Turn off hides the card and keeps the server off.
- **Notice.** While a workspace server waits for approval, a line under the header says so, with Review opening the list.
- **On and off.** Each server has a switch. Off stops the server and keeps it off for the workspace, in every chat, until it is switched on again. The engine keeps the choice in `~/.g-code/mcp-disabled.json`.
- **Rail.** An MCP call shows its server as a chip and its tool by its own name, as in `[userfake] echo {"text":"hi"}`.

## Forwarded servers

The extension passes ACP `mcpServers` in `session/new`, `session/load` and `session/resume`, and the engine trusts what the editor passes. So the extension forwards only servers the user owns: the user's VS Code `mcp.json`, in the user data folder beside `settings.json` (`packages/extension/src/chat/mcp-forward.ts`). It reads VS Code's JSONC, expands `${env:NAME}`, `${userHome}` and `${workspaceFolder}`, and leaves out a server that needs an `${input:...}` prompt, reporting why in the Geno engine output channel. It never reads the workspace's `.vscode/mcp.json`; the engine reads that file itself and holds its servers for approval. The panel labels forwarded servers "VS Code user settings".

## Cold start

A session's trusted servers start in the background as soon as the session opens (`McpSessions.register`). Each turn takes the tools of the servers that are ready when it starts (`McpHub.toolset`, which never waits), so a 30 second `npx` start no longer holds up the first answer. A server that becomes ready during a turn joins the next turn. The tool list of every model call in one turn stays the same bytes, so the cached prefix holds. `gcode agent`, which has a single turn, still waits for its servers (`McpHub.start`).

The panel asks for the servers again each second while one is starting.

## In the engine

- `session/close`, now advertised, stops the session's servers and cancels its turn. The log stays, and `session/resume` or `session/load` opens it again. The panel closes the chat it leaves for a new chat, a loaded one or a deleted one, so servers do not pile up.
- `_gcode/mcpTrust` takes `{ sessionId, name, hash }` and refuses a hash that is not the server's current definition.
- `_gcode/mcpEnable` takes `{ sessionId, name, enabled }` and answers with the servers, as `_gcode/mcpServers` does.
- `McpServerView.definition` is the definition as the trust card shows it (`mcpDefinitionView` in `packages/core/src/mcp.ts`).
- The server state machine has a `disabled` state, which remembers whether the server is trusted, so switching it on returns it to `stopped` or `untrusted`.

## Check

- `packages/extension/test/mcp.integration.test.ts` drives the real panel. The workspace's `.vscode/mcp.json` defines `wsfake`, and the user data folder's `mcp.json` defines `userfake`, both the fake stdio server from the engine tests. The test checks that `userfake` arrives forwarded and ready, and that `wsfake` stays untrusted with no marker file after a turn and is never offered to the model. It checks that the card shows the exact command line and env, that Allow starts `wsfake` (its marker appears and its tools join the next turn), that the switch turns a server off and on, and that the rail names the server of a call.
- Two defects were put in on purpose to see the test fail. Forwarding the workspace file as well fails with `the workspace server is not forwarded: it waits for approval; got "ready"`. A card showing only the program fails with `the trust card shows the exact command it would run`, naming what it showed and what it should have.
- Engine tests (`packages/engine/test/mcp-serve.e2e.test.ts`, `mcp.test.ts`) use a fake server that sleeps before answering (`DELAY_MS`). They check that the first model call goes out while the server is starting, that a server ready between two calls of one turn leaves that turn's tool bytes unchanged, and that the next turn has its tools. They also check that `session/close` ends the server process, that off and on persist and apply, and that a stale hash is refused.
- `pnpm tsx packages/extension/test/mcp-live.ts <dir>` trusts `chrome-devtools` from a copy of `~/Development/payload-site-template/.mcp.json` in a throwaway VS Code and waits for it to be ready through `npx`. It calls no model.
