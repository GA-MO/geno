# U46: deferred tools

Before U46, every tool a run offered went to the model in full on every call: Geno's own tools, the user tools, the widget, the subagent tools and every MCP tool. The browser alone adds 29 definitions. Past 40 MCP tools, an older lazy mode swapped them for `mcp_describe` and `mcp_call`. Now a run sends the core tools in full and every other tool by name and a one-line hint, in the description of one `tool_search` tool. The model loads a tool's definition with `tool_search` before its first call. The brief is the U46 line of "Harness ideas" in [plan-u19-on.md](plan-u19-on.md).

## Data shape

`packages/core/src/deferred-tools.ts` names it. It holds only types and pure functions.

- **The roster.** `ToolRoster` is `{ offered, deferred }`. `offered` is the request's `tools` array. `deferred` maps each deferred tool's name to its definition and hint, sorted by name. `toolRoster(tools)` builds it from every tool the run would offer:
  - The core tools stay in full: `read`, `grep`, `glob`, `list`, `edit`, `bash`, `check`, `ask_user`, `agent` and `todo` (`CORE_TOOL_NAMES`). `todo` stays in full because the model must see it to keep the pinned list (U56).
  - Every other tool is deferred. Today that is `bash_output`, `bash_stop`, `monitor`, `schedule_wakeup`, `skill`, `remember`, `show_widget`, `message_agent`, the editor tools `open_file`, `show_diff` and `reveal` (U54), `web_fetch` and `web_search` (U53), `recall` (U57), `read_terminal` (U55), `spawn_task` and `dismiss_task` (U48), and every MCP tool, the browser's included. The editor tools add about 397 tokens to what deferring saves (178, 127 and 92 by the roster's estimate). On their own they would save 66 net of `tool_search` and the note, under the threshold. With only `skill` beside them they would save 229. Plan also offers `web_fetch` and `recall`, which take it to 616, so Plan in an editor defers them. U55's `read_terminal` (about 248 tokens) takes that to 833, and U48's `spawn_task` and `dismiss_task` to 1,364. With `remember`, Plan saves 1,533; Ask and Auto save 2,876 with the widget, and Plan in the VS Code panel saves 2,206. `pnpm tsx scripts/roster-savings.ts` prints these numbers for every mode and client.
  - `offered` is the core tools in their usual order, then `tool_search`. When the deferred tools would save fewer than `MIN_SAVED_TOKENS` (300) net of `tool_search` and the note, nothing is deferred and `offered` is the input unchanged. Plan mode in the terminal was one such run until U57. Its only deferrable tools were `skill` and the web tools, which would save 98 tokens, or 188 with `web_search`. `recall` takes that to 302 and 392, so Plan in the terminal now defers `recall`, `skill` and the web tools. That is 2 tokens over the threshold, so a few characters cut from one of their descriptions would send them in full again.
- **The block.** `tool_search`'s description lists `- <name>: <hint>` for each deferred tool. The hint is the first sentence of the tool's description, cut to 90 characters. The block stays within 8,192 characters; past that, a closing line counts the tools left out, and `query` still finds them.
- **The load event.** A `tool-result` event of `tool_search` carries `loaded: string[]`, the names it made callable. Nothing else records a load.
- **The loaded set.** `loadedTools(events)` is the union of `loaded` over the `ok` results in the log. The session log loads through `cutView`, so a rewind that cuts a load also unloads the tool.
- **The search.** `searchTools(deferred, { select, query })` loads the exact names in `select`, and up to 5 best matches of the words in `query`, scored on the name and the description. The result text holds each definition as JSON (`name`, `description`, `input_schema`). A search that loads nothing is an error result that says why.
- **The refusal.** `unloadedCallError(deferred, loaded, name)` is the error for a deferred tool that was never loaded: "`<name>` is a deferred tool and is not loaded yet. Call tool_search with select: ["`<name>`"] first, then call `<name>` with the input its schema asks for."

`DEFERRED_TOOLS_NOTE` is one fixed sentence that follows the mode's system prompt in a run that defers anything.

## Why a load never changes the request's tools

A loaded definition reaches the model in the `tool_search` result, inside the conversation. It is never added to the `tools` array. The array and the system prompt stay the same bytes for the whole session, across loads, turns, resumes and reloads, so a load never invalidates the cached prefix. Model Studio's cache matches by prefix and the `tools` array comes first in it (research/competitors-2026-10.md, section 2.1). Adding a tool to the array would rewrite the whole cached prefix once per load.

This works only if the model calls a tool that is not in `tools` and the API accepts such a call in the history. Both were checked on Model Studio `qwen3.8-flash` before the design was chosen. With `tools` holding only `read` and `tool_search`, and a `tool_search` result holding a `browser_navigate` definition, the model called `browser_navigate` with a correct URL in 3 of 3 tries. The next request, with that call and its result in the history, returned status 200.

## Engine

- `runAgent` (`packages/engine/src/agent.ts`) builds the roster from the run's full tool list, MCP tools and the subagent tools included, once per run. It sends `roster.offered` and adds the note to the system prompt when anything is deferred.
- `rosterExecutors` (`packages/engine/src/tools/tool-search.ts`) adds the `tool_search` executor and wraps each deferred tool's executor. The wrapper reads the loaded set from the log on every call and refuses an unloaded call with `unloadedCallError` as an error result. A call in the same turn as its `tool_search` is refused too, because the load is logged with the turn's results. Before a loaded tool runs, `coerceToSchema` turns a string the schema types as a number, an integer or a boolean into that type (see Live run).
- `drive` copies `loaded` from the executor's reply onto the logged result, and the session log schema accepts it.
- The MCP hub declares every MCP tool directly again. The old lazy mode (`MCP_LAZY_THRESHOLD`, `mcp_describe`, `mcp_call`, `catalogText`) is gone, since the roster now defers MCP tools at any count.
- `docs/geno-tools.md` maps Claude Code's `ToolSearch` to `tool_search` for pstack skills.

## Tests

- `packages/core/test/deferred-tools.test.ts`: table tests for the roster (only core tools, one small rare tool, large rare tools, the browser, the eval configuration), the same `tool_search` bytes whatever order the tools arrive in, the block budget, hints, `searchTools`, `loadedTools` and the refusal text.
- `packages/engine/test/deferred-tools.e2e.test.ts`: through `gcode serve` with an editor-provided MCP server. The model calls `mcp__fake__echo` before loading it and gets the refusal as an error result. It loads it with `tool_search { query: "echo" }`, calls it, and gets `echo: one`. A fresh engine on the same store loads the session, and the model calls the tool again with no second `tool_search` and gets `echo: two`. All six requests carry the same `tools` and system bytes. The log holds `loaded: ["mcp__fake__echo"]` on the search's result. Dropping `loaded` from the logged result makes the test fail on the first echo.
- Tests whose fake model calls a deferred tool now load it first: `loadTools(...)` in `packages/engine/test/fake-transport.ts` builds the call, and `offeredTools(body)` reads what a request offers, block included. In the browser e2e, each session loads the browser tools in a first model call that the assertions skip. One wake test had passed only because its `schedule_wakeup` call failed. It now loads the tool and checks that the wake-up was set.

## Measurement

### Prefix tokens

`pnpm tsx scripts/prefix-tokens.ts` sends each configuration's tools and system prompt to Model Studio `qwen3.8-flash` with a one-word message and reads the input tokens the API reports, less the same message alone. "Deferred" forces deferral at any size, so it shows what each configuration would save.

| Configuration | Tools | Prefix tokens, all in full | Deferred | Prefix tokens, deferred | Saved |
| --- | --- | --- | --- | --- | --- |
| Eval (non-interactive, no MCP) | 12 | 4,160 | 5 | 3,567 | 593 |
| Editor, Ask, no MCP | 15 | 5,598 | 7 | 4,197 | 1,401 |
| Editor, Ask, browser and agent tool | 43 | 12,722 | 34 | 5,281 | 7,441 |

The same run measured 3.53 characters of tool JSON per token, which `toolRoster` uses (as 3.5) to estimate what deferring saves.

### The speed eval, before and after

`gcode eval speed` ran four times on 2026-10-07 (Bangkok time), interleaved: main at `c5c608e`, this branch, main, this branch. Every run used `--max-cost 0.10 --max-cost-per-task 0.035` to keep the total within the $0.40 budget. At that cap, main's runs stopped before task 4 of 5. The branch's runs reached task 5 and the end, so the comparison below uses the three tasks that every run finished: `payload-dayjs-bangkok`, `next-about-translations` and `next-counter-floor`. The load average (1, 5 and 15 minutes) was 9.61, 11.56, 12.46 at the start of the first run and 4.24, 4.35, 5.40 at the end of the last, on 10 cores with other agents running.

| Measure, on the three common tasks | Before, run 1 | Before, run 2 | After, run 1 | After, run 2 |
| --- | --- | --- | --- | --- |
| Load average at start (1 min) | 9.61 | 2.99 | 4.94 | 3.52 |
| Prefix tokens of each task's first call | 8,047 / 4,279 / 4,275 | 8,047 / 4,279 / 4,275 | 7,449 / 3,681 / 3,677 | 7,449 / 3,681 / 3,677 |
| Model calls | 56 | 53 | 59 | 39 |
| Input tokens per call | 10,729 | 11,290 | 9,297 | 7,841 |
| Cache-hit rate (cache read / all input) | 92.6% | 92.4% | 93.6% | 92.5% |
| Model time per call, p50 | 3.8 s | 5.2 s | 3.5 s | 3.5 s |
| Agent time per task | 150 / 131 / 124 s | 171 / 138 / 137 s | 139 / 103 / 71 s | 110 / 33 / 71 s |

| tool_search calls | 0 | 0 | 1 | 0 |

Over the six task runs of each arm, agent time per task has a p50 of 137 s before and 87 s after, and the pass rate is 6/6 in both.

What the numbers show:

- **The prefix fell by 598 tokens on every first call**, the same in both runs and on every task. That is the 593 tokens `prefix-tokens.ts` predicts plus the note. This is the effect U46 controls, and it is measured, not estimated.
- **The cache-hit rate held.** It moved within 92.4% to 93.6% in both arms. Nothing in the branch adds a cache miss: the `tools` bytes and the system prompt are the same on every call of a session.
- **The cost and time differences are mostly turn count, not the prefix.** 598 tokens on about 55 calls is about 33,000 tokens of about 600,000 input tokens per run, about 5.5% of the input. The second after-run cost half as much because the model took 39 calls instead of 53 to 59, which is run-to-run variance at n = 2 per arm. Do not read the drop in agent time or cost as a U46 speedup.
- **Loads were rare.** One run loaded `bash_stop` once, unprompted, after it had started a background command, and called it. No call to an unloaded tool was refused in any eval run.

### Threshold

A load costs one extra model call: on these tasks about 10,000 input tokens, mostly cached, and a few hundred output tokens, about 3.5 s. Deferring saves the deferred definitions, net of `tool_search` and the note, on every call. In the eval configuration that is 598 tokens over about 19 calls per task, about 11,000 tokens, so deferring pays while a task loads less than about one tool. The eval runs loaded 1 tool in 12 task runs. Browser and MCP configurations save 1,400 to 7,400 tokens a call, so they pay sooner.

`MIN_SAVED_TOKENS` is 300. Below it, `tool_search` would cost about as much as it saves, and a load would cost a turn on top. That keeps a lone `remember` (about 150 tokens) in full. Plan in the terminal was the other such case until U57 added `recall`, which takes it to 302 tokens saved.

## Live run

`packages/engine/test/browser-smoke.ts`, run with its budget cut to $0.0055, asks `qwen3.8-flash` through serve, in Auto, to open a local page, read its heading, click its button and report. The prompt does not mention `tool_search`.

The first run, before the input typing, failed. The model loaded `new_page` and `take_snapshot` with `tool_search` and opened the page. Then every snapshot call failed with "expected number, received string": it wrote `pageId` as `"2"` and `verbose` as `"False"`. With the same tools in the `tools` array, Qwen writes them typed, so this came from the schema arriving as text. It cost $0.0103 and hit 10 calls.

`coerceToSchema` now types such strings by the loaded schema before the tool runs. The second run passed in 5 tool rounds and cost $0.0058:

```
steps: tool_search mcp__browser__navigate_page mcp__browser__take_snapshot mcp__browser__new_page "browser navigate take_snapshot" | bash ls -a ... | mcp__browser__new_page {"url":"http://127.0.0.1:64147/"} | mcp__browser__take_snapshot {"pageId":2} | mcp__browser__click {"pageId":2,"uid":"1_2","includeSnapshot":true}
answer: The heading reads "Welcome to the Geno smoke page". After clicking the "Place order" button, the page shows the text "Thanks for clicking, the order is placed."
PASS
```

The log holds the model's own input, `"pageId":"2"`, and the step shows the typed `2`. The query loaded `click` with the named tools, so the click needed no second search.

## Known limits

- A forked subagent shares the parent's `tools` and system prompt, `tool_search` included, but not its executors. A fork that calls `tool_search` gets "unknown tool", as it did before for the parent's MCP tools.
- An MCP server that becomes ready mid-session changes the block, and so the prefix, once. That was true of the old MCP definitions too.
