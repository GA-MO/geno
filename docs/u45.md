# U45: background commands

The model can start a command that keeps running while it works, such as a dev server, a watcher or a long build. `bash` with `run_in_background: true` returns at once with a job id. The model reads the output with `bash_output` and ends the command with `bash_stop`. When a command ends by itself, the model hears of it at its next request. The brief is the U45 entry under "Harness ideas" in [plan-u19-on.md](plan-u19-on.md).

## Data shape

`packages/core/src/background.ts` names it.

- **Background job record.** `BackgroundJob` is `{ id, sessionId, toolUseId, command, description, pid, state, startedAt, endedAt, outputFile }`. `id` is a `JobId`, `bg-<n>`, numbered per session. `toolUseId` is the bash call that started the job, so the panel can find its step. `outputFile` is under the app home, in `spill/<session>/background/<id>.log`.
- **Job state.** `JobState` is a union on `status`:
  - `running`, with an optional `ending` that records a stop or a kill in progress.
  - `exited`, with the exit code and the signal.
  - `stopped`, with `by: 'model' | 'user'`.
  - `killed`, with `cause: 'session-deleted' | 'lane-discarded' | 'engine-exit'`.
- **State machine.** `nextJobState(state, input)` takes a stop, a kill or an exit. A stop or kill on a running job sets `ending`. The exit then reads as `stopped` or `killed`, whatever code the process returned. Without `ending`, the exit reads as `exited`. An ended job never changes again, and a second stop or kill keeps the first reason.
- **Who hears of the end.** `TELLS_MODEL` decides. The model hears of an `exited` job and of a job the user stopped. It does not hear of its own `bash_stop`, because the tool result already says so. It does not hear of a kill, because the session or the engine is going away.
- **End event.** `background-end` is a new session log event: `{ job: { id, toolUseId, command, state }, tail }`. The loop steps over it, as it steps over `restored`. `replayMessages` puts its text, `backgroundEndNotice`, after the tool results of the batch it came in, so it is part of the next request and does not start a turn by itself.
- **Limits.**

  | Constant | Value | What it bounds |
  | --- | --- | --- |
  | `MAX_BACKGROUND_JOBS` | 4 | Running jobs per session; a fifth start is refused with the ids that run |
  | `BACKGROUND_OUTPUT_CAP` | 1 MiB | Output kept per job, in memory and in its file; older bytes are dropped |
  | `STOP_GRACE_MS` | 3 s | Time between SIGTERM and SIGKILL |
  | `BACKGROUND_TAIL_LINES` | 20 | Lines an end notice carries (at most 2000 characters) |

## The tools

This is one deliberate change to the cached tool prefix and the system prompt. The definitions stay sorted and frozen.

- `bash` gains `run_in_background`. Its description says that the sandbox allows localhost and that a background command has no timeout.
- `bash_output { id, tail? }` returns the status and the exit code once the job ended. Without `tail`, it returns what the command printed since the last `bash_output` of it, and how many bytes were dropped before that read. With `tail`, it returns the last `tail` lines.
- `bash_stop { id }` sends SIGTERM to the job's process group and SIGKILL after the grace period. It returns once the job ended, with how it ended and its last lines.
- Plan mode has neither `bash_output` nor `bash_stop`, and refuses `run_in_background`. Subagents get neither tool, because a child ends with its call; `CHILD_TOOL_NAMES` in `core/src/agent.ts` leaves them out of every agent definition.

A background command goes through the same lane check, rules, classifier and approval as a foreground one. Then `Sandbox.spawn` wraps it with the sandbox's filesystem rules and starts it without waiting. The job holds the sandbox open with `Sandbox.retain` until it ends, so the turn that started it can close its own hold.

## The engine

- **`BackgroundJobs`** (`packages/engine/src/background.ts`) keeps every session's jobs for the engine process. Its two hooks are `changed`, for each start, each state change and new output (at most every 250 ms), and `ended`. It keeps the 8 newest ended jobs per session for `bash_output`.
- **`CappedOutput`** (`packages/engine/src/background-output.ts`) keeps the last 1 MiB in memory and in the file. It appends to the file and rewrites it from memory once it passes 1.25 MiB, so the file stays bounded without a rewrite per chunk.
- **Ids after a restart.** `jobIdsIn` reads the ids a session's log already used, so a job started after an engine restart does not reuse `bg-1`.
- **Delivery.** `Inbox` (`packages/engine/src/inbox.ts`) holds what reaches a session from outside its loop. `drive` takes the session's arrivals through `Mode.arrivals` at the safe point before each model call, after the tool batch, and logs them. When no turn runs, `logArrivals` logs them at once, behind the session's other writers. The next turn's first request then carries them. U44's steering message is meant to be another member of the `Arrival` union, delivered through the same `take` in `drive.ts`.
- **Lifetime.**
  - In `gcode serve`, the jobs live in `engineShared`, so they outlive their turn and a window reload. A window that loads the session gets each job's state after the replay.
  - The jobs are killed when their session is deleted, when their lane is discarded (any job whose folder is inside the lane), and when the engine exits. A socket engine kills them gracefully on its idle exit, and with SIGKILL from a `process.on('exit')` handler otherwise.
  - Running jobs do not keep the engine alive. Once no window is connected and no turn runs, the engine exits after 10 seconds and its jobs go with it.
  - A CLI run (`gcode agent`) keeps its jobs for that run only and kills them when the run ends.
- **Tasks.** `TaskRecord.jobs` lists the session's running jobs. `Tasks.jobs` updates it whether or not a turn runs.

## Sandbox change

`allowLocalBinding: true` is now set on the shared sandbox runtime. A command may bind a port on loopback and connect to `localhost`, which a dev server and its `curl` need. Every other host still goes through the allowlist, which is empty by default. On macOS one command can reach a server another command started. On Linux each command gets its own network namespace from bubblewrap, so that only works inside one command.

## Engine hooks

| Where | Does |
| --- | --- |
| `engineShared` | Adds `jobs` and `inbox` from `backgroundShared` in `background-hooks.ts`. |
| `gcodeAgent` | Sets `inbox.arrived` to log idle arrivals; passes `{ jobs, inbox }` to `runAgent`; logs leftovers when a turn ends. |
| `session/load` | Sends each job's state after the replay. |
| `session/delete` | Kills the session's jobs first. |
| `_gcode/lanes/discard` | Kills the jobs inside the lane. |
| `_gcode/backgroundStop` | New: stops a job for the user (`{ sessionId, id }`). |
| `daemon.ts` | Kills every job when the engine exits. |

A job's state reaches the panel as a `tool_call_update` for the bash call that started it, with the `JobView` under `_meta["gcode/background"]`. The replay sends the same update for each `background-end` event.

## In the panel

- A bash step with a job shows the end of the command's output in its OUT box, live, instead of the start line. Folded, it keeps the newest 4 lines and fades at the top.
- Under the box, a job row says "Running in background as bg-1" with a pulsing dot and a Stop button. Stop sends `_gcode/backgroundStop`; the row reads "Stopping bg-1…" until the job ends.
- When the job ends, the row becomes the notice: "bg-2 exited with code 0", "bg-1 was stopped by the user", or "was killed because …".
- The `background` action finds the step in any turn, since a job outlives the turn that started it.
- The Tasks pane lists each running job under its session, by id and description.
- The row fits at 300px.

## Deferred

- On Linux, one command cannot reach a port another command opened, because bubblewrap gives each its own network namespace.
- An engine killed with SIGKILL leaves its jobs running, since they run in their own process groups.
- A job stopped by the model logs no end event, so after a reload its step shows only the start line.
- The temp folder of the run that started a job is removed when that run ends.
