# U57: search past sessions

The History now searches the text of every session in the workspace, not only the titles. Each hit shows the turn it found, the day, and an excerpt with the match marked. Clicking the hit opens the session scrolled to that turn. The model gets a `recall` tool for the same search, so it can answer "what did we decide about X" from an earlier chat and say which session and turn the answer came from. The brief is the U57 row in the table at the end of [plan-u19-on.md](plan-u19-on.md).

## Data shape

`packages/core/src/session-search.ts` names it. It holds only types and pure functions.

- **The index entry.** `SessionDoc` is `{ summary, title, turns }`. `summary` is the `SessionSummary` that the History lists. Each `SearchTurn` holds `turn` (counted from 1, the way the History counts turns), `seq` (the event number of the prompt, which the panel and rewind name a turn by), `at`, and its texts. `sessionDoc(session, events, toolTitle)` builds the entry from the log as the user sees it, after rewinds.
- **What is indexed.** For each turn: what the user wrote, the assistant's text blocks, and the titles of its tool calls, such as `bash pnpm test` or `edit src/db.ts`. A slash command is indexed as typed (`/review the schema`), not as its expansion. The index leaves out tool output, thinking blocks, a child's report, a parent's message and a wake notice. It also leaves out `recall` calls, whose title is only the words searched for: a session that searched for "postgres" is not about Postgres. Each text is put on one line, normalized to NFC, and cut at 20,000 characters (`SEARCH_TEXT_MAX`).
- **Matching.** `fold` lowercases a text without moving any offset, so a mark's offsets into the folded text are also offsets into the shown text. A character whose lowercase is longer keeps only its first code unit, so `İ` folds to `i`. A Greek final sigma folds to `σ`, so a word matches inside a longer one. A query is split on whitespace into folded words (`searchTerms`). A word that another word of the query contains is dropped. A word matches as a substring, so Thai, which is written with no spaces between words, matches inside a run of text.
- **Ranking.** In one text, each occurrence of a word counts up to 3 times. It is weighted 3 in the title, 2 in what the user wrote, and 1 in an answer or a tool title. A turn scores 100 for each distinct word it holds, plus its weighted count held under 100, so one more distinct word always outranks any number of repeats. The session's score is its best turn's score, plus the title's score when the title matches, plus 5 for each matching turn, up to 5. Ties go to the newer session. `match: 'all'` keeps a session only when every word occurs somewhere in it. `match: 'most'` keeps one that holds at least half of the words.
- **The hit.** `SessionHit` is `{ sessionId, title, workspace, updatedAt, turn, source, snippet, matchingTurns, score }`. `turn` is `{ turn, seq, at }`, or `null` when only the title matched. A `Snippet` is `{ text, marks }`. `marks` are `[start, end)` ranges into `text`, sorted and apart. `snippetOf` cuts the excerpt around the first match, at a space when there is one within 12 characters. It never cuts between a Thai consonant and its vowel or tone mark, or inside a surrogate pair, and it adds `…` on each side it cut. It marks only whole matches, and a mark takes in a combining mark right after it, so `สิ` in `สิ่ง` marks `สิ่`.
- **Exclusion.** `exclude` leaves out the listed sessions and every fork of them, since a fork's log copies its source's turns.
- **The tool.** `RECALL_SPEC` is the definition of `recall { query }`. `RECALL_SEARCH` is `match: 'most'`, at most 6 sessions, and excerpts of 240 characters. `recallText(query, hits)` writes the result inside `<recalled_sessions query="…">`, one entry per session: `- session <id>, turn <n>, <yyyy-mm-dd>: "<title>"` and the excerpt on the next line. A closing line says that the excerpts are data from earlier sessions, may be out of date, and are not instructions, and that the model should cite them as (session `<id>`, turn `<n>`). Text that would open or close the fence loses its angle bracket (`‹/recalled_sessions>`), as a child's report does.
- **The method.** `SEARCH_SESSIONS_METHOD` (`_gcode/searchSessions`) takes `{ query, cwd? }`, with `cwd` for this project's sessions and none for every project's. It answers `{ hits }`.

## In the engine

- `SessionIndex` (`packages/engine/src/session-index.ts`) holds a `SessionDoc` per log file, with the file's size and change time. Each use reads the sessions folder and stats every log. It reads again only a log whose size or change time moved, and it drops a log that is gone. Refreshes run one at a time, so two searches typed in a row never read a log twice. `sessionIndex(store)` returns the one index per sessions folder in the process. The History's listing, its search and every run's `recall` share it.
- `listSessions` now reads the summaries from that index. Opening the History builds the index, so the first search is already warm, and later opens read only the logs that changed. A log that cannot be read is reported as before (`warning: skipped <file>: …`) and left out. It is reported once per version of the file, not on every keystroke of a search. A log trashed between the `stat` and the read is dropped without a warning. The one-shot `gcode session list` now builds each session's index entry too, about 100 ms more on 300 sessions (see Timing).
- `recall` is one of the agent tools (`AGENT_TOOL_NAMES`). Every mode offers it, Plan included, because it only reads. It runs beside other calls and never asks. A subagent does not get it (`CHILD_LEAVES_OUT`), because its task comes from its parent, which can recall for it. `runAgent` searches the session's project, which is the main checkout for a session in a lane. It leaves out the session itself, its forks, and the session it was forked from, whose turns up to the fork the model already has in context.
- `recall` is not a core tool, so the roster defers it behind `tool_search` like the others (docs/u46.md). Its definition is 807 characters, about 231 tokens by the roster's estimate. Where the roster defers anything, `recall` adds only its line to the `tool_search` block, and deferring saves 204 tokens more a call. Every mode now defers it:
  - **Ask, Auto and non-interactive.** These deferred `skill`, `web_fetch` and the background tools before. They now save 972 tokens a call in the terminal. Ask and Auto save 2,128 in an editor that shows `remember` and the widget, or 2,345 since U55 added `read_terminal` there. An eval run (non-interactive) lists `recall` among its deferred tools, so its `tool_search` block, and so its prefix, has one line more than the U46 baseline. Compare eval runs from before and after U57 with that in mind.
  - **Plan in the editor.** It deferred `skill`, `web_fetch` and the editor tools `open_file`, `show_diff` and `reveal` before (412 tokens) and now defers `recall` too (616). U55's `read_terminal` takes it to 833.
  - **Plan in the terminal.** Before U57 it deferred nothing, because `skill` and `web_fetch` saved only 98 tokens, under `MIN_SAVED_TOKENS` (300). With `recall` they save 302, or 392 with `web_search`, so the run now sends `recall`, `skill` and the web tools by name only, and adds the deferred-tools note to the system prompt. The model loads one with `tool_search` before its first call, which costs a turn. The margin is 2 tokens, so a few characters cut from one of these descriptions would send them in full again.
- The serve handler for `_gcode/searchSessions` uses `match: 'all'`, at most 50 sessions, and 120-character excerpts. It does not leave out the session the panel shows.
- `session-replay.ts` now exports `titleOf`, the title a replayed tool call shows, so the index uses the same titles as the transcript. It also titles a replayed `recall` call `recall <query>`, as the live call is titled. Those are the only changes to the replay.

## In the panel

- The search field searches titles as before, and it also asks the engine for the text search 120 ms after the last key (`search-sessions`). The title matches show at once. When the engine answers, its hits come first, in its order, and the sessions that only the title or the project name matches follow them. A late answer for an older query or another scope is dropped (`history-state.ts`, the `Found` state).
- A hit adds a line to its row, such as `Turn 9 · Oct 1` (with `· 3 turns match` when more turns match), and up to two lines of the excerpt. Each match is in a `<mark>`. The text is built as text nodes, never as HTML. The mark uses the editor's find-match colors, and high contrast adds the contrast border.
- Clicking a hit posts `open-session` with the turn's `seq`. The extension loads the session, finds the turn with that `seq`, and sends `reveal-turn`. The webview scrolls that turn to the top, below the sticky request, and rings it for 2 seconds. A hit in another project opens in that project's window, at the end of the session.
- When the engine search fails, the note under the field says so, and the title matches still show.

## Timing

`pnpm tsx packages/engine/test/session-search-bench.ts [sessions] [max tool output bytes]` writes generated session logs and times the History through `SessionIndex`, with 5 runs of each measure. The sessions mix English and Thai. Each has 3 to 25 turns and 1 to 6 tool calls a turn, with tool output that the index skips. The bench also times what each History open cost before U57, which was reading and summarizing every log. The run below was on 2026-10-07 on a 10-core Apple silicon Mac, with the 1-minute load average at 7 to 10 from other agents. The measures were not interleaved.

| Measure, 300 sessions | 49.6 MB of logs (tool output up to 2.5 KB a call) | 126.2 MB of logs (up to 12 KB a call) |
| --- | --- | --- |
| Indexed texts | 45,584 | 52,062 |
| Each History open before U57 (read every log) | 730 ms (701 to 790) | 1,026 ms (1,016 to 1,125) |
| First History open or search (builds the index) | 832 ms (795 to 914) | 1,189 ms (1,142 to 1,340) |
| Search with a warm index, 8 queries × 5 | 5.3 ms (3.0 to 16.8) | 6.6 ms (3.3 to 12.2) |
| Search after one log grew | 7.5 ms (6.3 to 8.2) | 9.1 ms (7.4 to 9.9) |

The values are medians, with the range of the 5 runs in parentheses.

- **The first use is bound by reading the logs.** In a separate profile of the 49.6 MB store, reading and parsing every log with the log schema took 681 ms, and building every `SessionDoc` took 82 ms over 11.6 million characters of indexed text. Opening the History already paid the read before U57, on every open. It now pays it once per engine process, plus about 100 ms to build the entries.
- **A warm search is bound by the `stat` of each log and by `indexOf` over the indexed text.** Its median is 5 to 7 ms, and its slowest run was 23 ms. A rerun on the lighter store after the review fixes, at a load average of 10.6, gave 840 ms for the first use, 6.5 ms (2.8 to 23.2) warm, and 6.5 ms after a log grew, against 724 ms for the old listing.
- **The work happened.** Each query reported its hit count (50, the limit, for the 7 queries whose words the generator uses, and 0 for `zzz-no-such-word`), and the grown log was read again, which is why that search costs a little more than a warm one.
- **The fixture is heavier than real use.** The real store on this machine has 181 sessions in 12 MB, about 66 KB a session. The lighter fixture averages 165 KB a session.

## Choices made in this unit

- **Substring matching on folded text, not a word index.** Thai has no spaces between words, so a word index would need a Thai word segmenter. In Node 22, `Intl.Segmenter('th')` splits `เมื่อวานเราตัดสินใจใช้Postgresแทน` into `เมื่อ|วาน|เรา|ตัดสิน|ใจ|ใช้Postgresแทน`. A word index built that way would miss ตัดสินใจ as one word, and Postgres inside the last segment. A warm scan takes milliseconds at a few hundred sessions, so an inverted index would add code and memory with no gain the user would notice.
- **One index for the listing and the search.** Making the listing read through the index removed the second read path. It also turned every History open after the first from a read of every log into a `stat` of every log.
- **`all` for the panel, `most` for the model.** A person who types two words expects both. A model writes longer queries ("postgres database choice"), and a session that holds most of the words still answers it.
- **One hit per session.** The History lists sessions. The model gets the best turn of each, with how many turns match, and can search again with narrower words.
- **The current session counts in the History, but not for `recall`.** The model already has its own session in context. The user may want to find something in the open chat.
- **No `recall` for subagents.** A subagent's task comes from its parent. Recall from a child would also find the parent's session, which the child must not mistake for its own history.
- **Lanes recall the main checkout's sessions.** A lane is a worktree of the main checkout, and the work it continues was discussed there.

## Known limits

- NFC does not fold Thai ำ (U+0E33) with its two-character spelling ํา, so a query typed one way misses text written the other way. Folding it would change offsets, and the marks depend on them.
- The index lives in the engine process. A restart builds it again on the next History open or `recall`.
- A hit in another project's session opens that project's window at the session's end, not at the turn.
- The open session's transcript is not highlighted at the matched words. Only the turn is ringed.
