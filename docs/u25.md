# U25: lanes in the panel and background sessions

U24 gave the engine lanes. U25 shows them in the chat panel and lets work run in the background. A Lanes pane lists each lane with its task, status, diff stat, check result and cost, and offers Open, Apply and Discard. The composer's send menu has Run in a new lane. A turn keeps running in the engine when the panel closes, when the user moves to another chat, and when the window reloads. A Tasks pane lists running and finished sessions, and a notification fires when a task finishes, fails or needs input. The brief is the U25 section of `research/competitors-2026-10.md` section 5, with sections 3.3 and 3.4.

## Data shape

`packages/core/src/tasks.ts` names it.

- **Background-session record.** `TaskRecord` is `{ sessionId, title, workspace, lane, status, startedAt, endedAt, usage }`. `lane` is the lane name or null. `usage` is the turn's model, tokens and cost so far. `status` is a `TaskStatus`:
  - `running`: the turn runs.
  - `needs-input`: a permission or question card waits for the user.
  - `done`, `failed`: the turn ended by itself.
  - `stopped`: the user stopped it.
- **How a turn's end becomes a task end.** `TURN_ENDS` in `packages/engine/src/serve.ts` maps each end of the loop to the task's end, an Arena lane's end, a scheduled run's end and ACP's stop reason. ACP has no stop reason for a failed model call or for the budget, so the prompt response also carries the task end, a `TaskEnd`, under `_meta["gcode/turnEnd"]`. The panel reads done, failed or stopped there, not from the stop reason.

  | The loop ended on | Task | Arena lane | Scheduled run | ACP stop reason |
  | --- | --- | --- | --- | --- |
  | The model's answer (`end_turn`) | `done` | `done` | `done` | `end_turn` |
  | The limit on model calls (`max-turns`) | `failed` | `capped` | `max-turns` | `max_turn_requests` |
  | The cost limit (`budget`) | `failed` | `capped` | `budget` | `max_turn_requests` |
  | A refusal | `failed` | `failed` | `failed` | `refusal` |
  | A model error, such as an HTTP 400 or the output limit (`error`) | `failed` | `failed` | `failed` | `end_turn` |
  | The user's stop | `stopped` | `stopped` | `stopped` | `cancelled` |

  A lane apply, a built-in command and a wake with nothing to take have no loop, and end as an answer.
- **Notification trigger table.** `TASK_NOTICES` maps the status a task moves to onto a notice. `taskNotice(from, to)` applies it and says nothing when the status did not change.

  | Moves to | Notice | Severity |
  | --- | --- | --- |
  | `running` | none | |
  | `needs-input` | "Geno needs your answer: …" | warning |
  | `done` | "Geno finished: …" | info |
  | `failed` | "Geno failed: …" | error |
  | `stopped` | none, the user did it | |

- **Lane view model.** The engine sends `LaneInfo`: `{ name, path, branch, status, createdAt, diff, check, session, task }`. `diff` is a `DiffStat` (files, lines added, lines removed). `check` is `passed`, `failed` or `none`, read from the last check line an edit wrote. `session` holds the task's title, turns and cost. `task` is the session's `TaskStatus` while the engine knows it. In the panel, `laneRowOf` in `packages/extension/src/chat/lanes-model.ts` turns a `LaneInfo` into a `LaneRow`: the badges, the diff text, the cost, and `actions`, which is `{ open, apply, discard }`. `discard` is `off` while the task runs or waits, `confirm` for a lane with changes, and `plain` otherwise. `taskRowOf` does the same for a `TaskRecord`.
- **Lane apply event.** `lane-apply` is a new session log event: `{ lane, changes, conflicts, deleted }`. `reviewState` counts its changes like an edit's, so the hunks stay under review after a reload. A replay shows it as a turn of its own.

## The engine process

Before U25 each window ran `gcode serve --stdio` as its child, so a reload ended every turn. Now the engine is a process of its own on a Unix socket, `gcode serve --socket <path>`.

- **One per folder and settings.** `socketPathOf` hashes the CLI path, the folder, the engine's variables and the `GCODE_*` variables. Windows of one folder share an engine, and a reloading window finds it again. A changed key or model names another socket, so the old engine ends once its turns do. The key goes in only as part of the hash. The socket is `0600`, in the user's temp folder, or in `/tmp` when that path would pass macOS's 104-byte limit.
- **Start and stop.** The extension dials the socket. If nothing answers, it starts the engine with `detached: true`, so the engine outlives the window, and writes its stderr to a log beside the socket. The output channel follows that log. The engine exits 10 seconds after the last window leaves while no turn runs. A second engine that finds the socket taken exits at once.
- **Shared state.** `engineShared` holds what outlives one connection: turns, modes, Auto state, log writers, tasks, and each running turn's events and unfinished text. `gcodeAgent` builds one ACP app per connection over it. `--stdio` still serves one editor, as Zed runs it.
- **Which window shows a session.** `Viewers` in `packages/engine/src/viewers.ts` maps each session to the connection that shows it, set by `session/new`, `session/load`, `session/resume` and `session/prompt`, and cleared by `_gcode/detach`, `session/close` or a closed connection.
  - A turn sends its updates to that window, and drops them while none shows the session. The log keeps them for the next load.
  - A turn reads and writes files through that window's buffers, and through the disk while none shows it. A lane session always uses the disk, since its review is the apply.
  - A question waits for a window that shows the session. If the window goes away, or answers with `NOT_SHOWN_ERROR` because the user left the session, the question goes to the next window. The task reads `needs-input` while it waits.
- **Load during a turn.** The load takes the turn's events and unfinished text in one step, with no await in between. It holds the turn's new updates until the replay is out, so the window sees each update once and in order. The response's `_meta["gcode/running"]` says the turn still runs.

## Engine hooks

Each is a small named handler in `serve.ts` that calls U24's functions through `packages/engine/src/lane-hooks.ts`.

| Method | Does |
| --- | --- |
| `_gcode/tasks` | Lists the tasks, newest first, and the notices no window was connected to hear, each once. |
| `_gcode/taskUpdate` | A notification to every window that advertises `gcode/tasks`, on each change, with the trigger table's notice. |
| `_gcode/detach` | The window stops showing a session; its turn goes on. |
| `_gcode/lanes` | `listLanes`, with `laneDiffStat`, the last check, and the session's title, cost and task. |
| `_gcode/lanes/new` | `createLane` from HEAD, named from the prompt by `laneNameFor`, with `copyIncluded` and `cloneDeps`. Setup runs only if the user approved it before with `gcode lane new --approve-setup`. The prompt then runs in a new session in the lane, in the background, in the mode new chats start in. |
| `_gcode/lanes/discard` | `discardLane`. A lane with changes needs `discardChanges`. A lane whose task runs or waits is refused. |
| `gcode/laneApply` in a prompt's `_meta` | `applyLane` and `writeLaneChanges` as a turn of the shown chat (below). |

`laneDiffStat` is the one function added to `lanes.ts`. It diffs the lane's working tree, untracked files included, against the lane's base.

Lanes share one network allowlist, because sandbox-runtime keeps one configuration per process, and every lane session runs in the same engine process.

## In the panel

- **Lanes pane.** The title bar's Lanes action opens it. Each row shows the lane name, the task, a status badge, the diff stat such as "+1 −1 · 1 file", the check badge and the cost.
  - Open shows the lane's session in the panel.
  - Apply returns to the chat and applies the lane there.
  - Discard removes a lane with nothing to lose at once. For a lane with changes it opens an inline confirm, with the keyboard on Cancel. The confirm stays inside the panel, because VS Code's modal dialog is native on macOS.
  - An empty pane says what a lane is and where to start one.
- **Apply.** The chat sends the prompt "Apply lane <name>" with `gcode/laneApply`. The engine takes a checkpoint and writes each file through the editor as an edit step. The editor puts each hunk under review as it does an agent's edit, so the diff cards have Keep and Undo per hunk, and the CodeLens has them in the file. The checkpoint lets the session's Undo take the whole apply back. The turn ends with "Applied 1 file from lane …", or with the conflict list, and then nothing is written. A deleted file is deleted on disk and named in the text, since a hunk cannot undo a deletion.
- **Run in a new lane.** A chevron beside Send opens the send menu: Send, and Run in a new lane. The menu has the mode menu's keys. The draft becomes the lane's task, the composer clears, and the Lanes pane opens on the new lane. The chevron goes with Send: while a turn runs, Enter queues, and the running row keeps the room U23 measured. A lane's prompt is its text only; `@` mentions and attachments stay with the chat.
- **Tasks pane.** The title bar's Tasks action opens it. Running tasks come first, then the rest, newest first. Each row shows the title, the lane or "Main checkout", the time and the cost, with Open, or "Shown in the chat" for the panel's own session, and Stop while it runs. The view's badge counts the tasks running in the background.
- **Leaving a running chat.** New Chat, History and Open now move away from a running turn instead of refusing. The turn goes on in the background, and its open cards go back to the engine. Before, New Chat and History said to stop the turn first.
- **After a reload.** The window loads the session it showed. A turn still running stays open in the transcript, with Stop, and its live updates follow the replay. The task's end ends it, with the task's usage in the footer.
- **Escape.** An Escape that closes a pane no longer also stops the running turn. The stop handler skips an Escape a pane already took. This was true of the MCP pane too.

## Notifications

Geno uses VS Code's notification API, and also macOS's own notification through `/usr/bin/osascript` when the window is not in front. `channelsOf` in `packages/extension/src/chat/notices.ts` decides:

| The user | VS Code notification | macOS notification |
| --- | --- | --- |
| looks at the session in a focused window | no | no |
| is in the window, on another session or with the panel hidden | yes, with Open | no |
| is in another app | yes | yes |

VS Code's notification stays inside its window, so it cannot reach a user who is in another app. `osascript` is the system's own tool, so this needs no new dependency. The text goes in as the script's arguments (`on run argv`), never into the script source, so a task title cannot run as AppleScript. The setting `gcode.tasks.osNotifications` turns the macOS one off; the test launcher sets it off.

## Deferred

- The task list lives in the engine process. When the last window leaves and no turn runs, the process exits, and the finished tasks go with it. The sessions stay in History.
- A window shows one session at a time. A lane's session opens in place of the chat; History or Tasks goes back.
- Lane setup commands run only when approved before through `gcode lane new`. The panel does not ask that question.
- A lane apply's deleted file is not under per-hunk review.
- A replayed apply in a temp folder under `/var` shows the file's folder beside its name, because the engine logs the real `/private/var` path. Agent edits replay the same way. User folders without a symlink in their path are not affected.
