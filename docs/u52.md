# U52: remembered permission rules

A command's approval card now offers **Always allow in this workspace**. It saves an allow rule, and the next time the same command runs in that workspace Geno does not ask in Ask mode or call the classifier in Auto mode. Settings lists the workspace's rules under **Permissions**. There the user can remove each rule and type new allow or deny rules. A deny rule blocks its command without asking, in every mode but Plan. The contract is the U52 row in [plan-u19-on.md](plan-u19-on.md).

## Data shape

All matching is pure, in `packages/core/src/permission-rules.ts`.

- **`CommandPattern`** is a program and its fixed leading arguments, quotes removed: `pnpm vitest run` is `['pnpm', 'vitest', 'run']`.
- **`PermissionRule`** is `{ id, effect: 'allow' | 'deny', pattern, createdAt }`.
- **`PermissionsFile`** is the store record: `{ version: 1, workspace, rules }`. There is one file per workspace, `$GCODE_HOME/permissions/<sha256 of the real path>.json`, written whole through a rename. A lane shares its main checkout's file. Nothing is written into the repository.
- **`RULES_IN_MODE`** says which rules each mode honours.

| Mode | Deny rules | Allow rules |
| --- | --- | --- |
| Plan | no | no |
| Ask | yes | yes |
| Auto | yes | yes |
| Non-interactive | yes | no |

- **`Denial.offer`** is the allow rule a question offers to save. It is set only when one simple command of the line needs a rule and a pattern can cover it.
- **`isHardAsk`** in `approval.ts` names what no rule may pre-allow.

### Decision table

`ruledDenial(command, scope, mode, rules)` decides a line in this order. The built-in verdict is what `denialFor` returned before U52.

| Step | When | Outcome |
| --- | --- | --- |
| 1 | Plan | the built-in verdict |
| 2 | a deny rule matches any simple command | denied, without asking or classifying |
| 3 | the built-in rules flag nothing | runs |
| 4 | allow rules are honoured, and every flagged simple command is covered | runs, unasked and unclassified |
| 5 | otherwise | the built-in verdict, with `offer` when one simple command needs a rule |

A flagged simple command is covered when all three hold:

- It is no hard ask.
- Its words start with an allow rule's pattern.
- The pattern on its own earns every built-in rule that flags the command.

So `pnpm vitest run` covers `pnpm vitest run src/a.test.ts`. It does not cover `pnpm vitest run ../../x`, because the outside path flags that command and the pattern alone does not.

### Hard asks

No allow rule covers these, and Settings refuses to save an allow rule for one:

- an `rm -rf` the workspace cannot spare (the `rm-rf-outside-workspace` rule);
- a `git push` that forces, mirrors, deletes or prunes, pushes `+ref` or `:ref`, or pushes to a URL or an `user@host:` address instead of a named remote;
- any command that names credentials, a hidden glob or a path under `.git`, an option's `=value` included.

### Matching

Matching is on the words `splitCommand` returns, so quotes are removed and operators split the line.

- **Allow** compares the words as written. `env pnpm …`, `FOO=1 pnpm …`, `./pnpm …`, `$P vitest run` and `'pnpm vitest run'` do not match `pnpm vitest run`.
- **Deny** also looks through wrappers, assignments and a program named by path, and it checks every value a variable may hold. A program word that is known only at run time, such as `$(echo pnpm) publish`, stands for any program.
- **Compound lines.** Every simple command the built-in rules flag must be covered, the commands of `$(…)` and backticks included. A simple command the built-in rules leave alone needs no rule. So `pnpm vitest run 2>&1 | tail -20` and `cd packages/core && pnpm vitest run` match `pnpm vitest run`. `pnpm vitest run && curl https://x` and `pnpm vitest run | sh` do not.
- **The offer** is the program and up to two subcommand words, grown word by word until the pattern earns every flag on the command. For example, `git push origin main` offers `git push origin`, and `rm -rf node_modules` offers `rm -rf node_modules`. No offer is made for a lone program, a computed word, a shell, `sudo`, `env` or `xargs`, an interpreter's inline-code flag such as `python3 -c`, or a line with two flagged commands.

## Engine

- `packages/engine/src/permissions.ts` is the store: `list`, `add` (one rule per pattern, so saving twice keeps one) and `remove`. `rulesWorkspace` resolves a lane to its main checkout.
- The bash tool reads the rules before each command, so a change in Settings applies to the next command. `settle` now takes `keep(answer)`, which it awaits for `allow-session` and `allow-workspace`. For a bash command, `allow-workspace` saves `denial.offer`.
- `gcode serve` adds a third option, `allow-workspace` ("Always allow in this workspace"), when the denial has an offer, and puts the pattern in `rawInput.rule`. It comes after Allow once and Reject.
- A `workspace-deny` rule id joins `APPROVAL_RULE_IDS`. Its tool result tells the model which rule stopped it.
- Extension methods: `_gcode/permissions`, `_gcode/permissionAdd { effect, text }` and `_gcode/permissionRemove { id }`. Each answers with `{ workspace, rules }`. `permissionAdd` parses the text with `parseRule` and answers invalid params with the reason when it refuses.
- An external agent's questions are unchanged. Geno still answers them with `allow_once` or `reject_once`, never an `_always` option, and their cards offer no workspace rule.
- MCP tools keep "Allow this tool for the session". They get no workspace rule in this unit.

## In the panel

- **Card.** A command card with an offer shows "Always allow saves the rule `ls ..` for this workspace. Settings lists its rules." Its buttons are Allow and Deny, then "Always allow in this workspace" as a secondary button. Once chosen, the card reads "Allowed, and saved as a rule for this workspace".
- **Settings.** The Permissions section, after Providers, lists the workspace's rules, each with an Allow or Deny chip, its pattern and Remove. Under the list, a form takes Allow or Deny and a command, then Add. A refused rule stays in the field, with the engine's reason under it. The list comes from the engine through the shown session.

## Choices made in this unit

- A simple command that the built-in rules do not flag needs no rule, so a covered command piped into `tail` still matches. The plan row says "compound commands refused". This keeps that rule's safety, because such a command would run unasked on its own. Requiring a rule for `tail` would leave Auto asking about almost every test run.
- A rule covers only the flags its own words earn. A rule never turns into a blanket pass for its extra arguments.
- A deny wins over a hard ask too. The order in the brief puts hard asks first, but denying is the safer of the two answers.
- Non-interactive runs follow deny rules and ignore allow rules. The user saved an allow while watching a session, not for an unattended run.
- Rules are keyed by the main checkout, so a lane follows its project's rules.
- No MCP workspace rule yet.
