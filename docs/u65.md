# U65: read PDFs and notebooks

The `read` tool now reads PDFs and Jupyter notebooks. Specs and reports often arrive as PDFs, and before U65 the model got only "binary file" for one. The contract is the U65 row in the table at the end of `docs/plan-u19-on.md`. Editing notebooks stays for later.

## What the model sees

`read { path: "report.pdf" }` returns the page count, then each page under a marker:

```
report.pdf is a PDF with 2 pages.
--- page 1 of 2 ---
Quarterly Report
Revenue grew to 4,210 units in the third quarter.
--- page 2 of 2 ---
Appendix
The launch code word is PELICAN-42.
```

- **Pages.** `pages` takes `"3"`, `"2-5"` or `"21-"`. The default is the first 10 pages. One read returns at most 20 pages, and a range of more than 20 is an error that names the range to ask for. A read that leaves pages out ends with the `pages` value that continues it.
- **Scans.** A page with no text layer that draws an image is a scan. Read returns its largest image through the image path, as for a PNG file: `[page 1: 400x200 JPEG image (8 KB), attached below as image 1]`.
- **Notebooks.** `read { path: "analysis.ipynb" }` returns each cell's number, type and execution count, its source, and its outputs. A stream, error or text output is shown in full up to 4,000 characters. An image output (PNG, JPEG, GIF or WebP) goes through the image path. `cells` picks cells the way `pages` picks pages. `start_line` and `end_line` still read the notebook's raw JSON.
- **Errors.** An encrypted PDF, a file with no `%PDF-` header and a PDF whose page tree is gone each fail with one line that says which. A notebook that is not JSON, or not nbformat 4, fails and points to `start_line`.

## Data shape

- `PdfPage` in `packages/engine/src/tools/pdf.ts` is a union: `text`, `scan` (the image bytes), `unreadable` (a reason, such as a JBIG2 scan or a font with no Unicode map) and `blank`. `openPdf(bytes)` returns `{ pageCount, page(n) }`, and pages are read on demand.
- `Section` in `sections.ts` is one PDF page or one notebook cell: a heading and a list of text and image parts. `readSections` is the one place that applies the reply's limits, so PDFs and notebooks share them.
- The PDF object model in `pdf-syntax.ts` is a closed set of values: `Name`, `Ref`, `Stream`, dictionaries as maps, strings as bytes, numbers, booleans, null and arrays.

## Limits

| Limit | Value | Where it comes from |
| --- | --- | --- |
| File size of a PDF or notebook | 64 MB | `MAX_DOCUMENT_BYTES` in `read.ts`; both are parsed whole in memory |
| Text in one reply | 20,000 characters | `PAGE_MAX_CHARS`, as for text files. A read stops at a page or cell boundary. A single section longer than that is cut. |
| Images in one reply | 8 images, 5 MB | `MAX_IMAGES` and `MAX_MESSAGE_BYTES`, as for attachments. A page or output over the limit is named, with the read that shows it. |
| Image side | 8,000 pixels | `MAX_IMAGE_SIDE` in `storeImage`. A raw-pixel scan is scaled down to 1,568 pixels on its long side before it is encoded, which is the side the model reads without resizing. |
| One decoded stream | 64 MB | `MAX_STREAM_BYTES`, so a small file cannot inflate into gigabytes |
| Drawing operators on one page | 2,000,000 | `MAX_OPERATORS` |
| Pages in one request | 20 (default 10) | the contract |
| One notebook output | 4,000 characters | `OUTPUT_MAX_CHARS` |

Readable roots are unchanged: a PDF or notebook must resolve inside the workspace or a read root, through `resolveInside`, as every other file does.

## How PDF text is extracted

The extractor is about 1,100 lines in three files, with no new dependency.

- **Objects.** `pdf-syntax.ts` tokenizes PDF syntax. `pdf.ts` finds every object by scanning for `n g obj` rather than trusting the cross-reference table, which is often wrong in damaged and incrementally saved files. It skips over stream data, so bytes inside a stream are never taken for objects, and the last definition of an object wins. It expands compressed object streams (`/ObjStm`), as PDF 1.5 writers produce them.
- **Filters.** Flate (with PNG predictors), ASCIIHex and ASCII85. A stream with another filter, such as LZW, makes that page `unreadable` with the filter's name.
- **Fonts.** `pdf-fonts.ts` decodes text through the font's ToUnicode CMap first. Then it uses `/Differences` glyph names, the encoding built into an embedded Type 1 font, and then WinAnsi, MacRoman or Standard encoding. Composite (Type0) fonts split codes by the CMap's code space. Glyph widths come from `/Widths` and `/W`.
- **Layout.** The walker follows the text matrix and the CTM through `q`, `Q`, `cm`, form XObjects and the text operators. It starts a line when the text moves down by half a line, and puts a space where the next glyph starts more than 0.15 em past the last glyph's end. It works per glyph, because some writers open word gaps with character spacing inside one string. `/ActualText` replaces the glyphs it covers, as for ligatures.

Measured against `pdftotext` on the bash manuals in `/usr/share/doc/bash` (four groff and Ghostscript PDFs, 106 pages), the extractor's words match 96 to 99 percent of `pdftotext`'s. The gap is mostly words hyphenated across lines, which `pdftotext` joins. The 65-page `bash.pdf` takes about 160 ms. A fuzz run over 400 truncated and bit-flipped copies of the fixtures raised only `PdfError` or returned pages. The longest file took 120 ms.

### Security

Text extraction reads the page tree, fonts, content streams and image streams, and nothing else. It never reads `/OpenAction`, `/AA`, `/JavaScript`, `/AcroForm` or annotations, so there is no code path that could run them. Content stream operators are a fixed switch on the operator name, and an unknown operator is ignored. A test puts a JavaScript `OpenAction` and a form field in a PDF and checks that only the page text comes back. Page text is data in a tool result, as file contents are.

### What it does not do

- It does not render pages. A scan's page is the image the scan holds: a JPEG (DCT) passes through unchanged, and raw pixels (gray, RGB, CMYK, indexed, 1 to 8 bits) become a PNG. JPEG 2000, CCITT fax and JBIG2 scans are `unreadable` with the format's name. A page that mixes a little text with a large image is read as text.
- It does not decrypt. An encrypted PDF fails, even one with an empty user password.
- It does not read text in Type 3 glyph procedures, or in a font with no ToUnicode and no standard encoding, such as a subset CID font without a map. Such a page says so.

## Why not a dependency

The brief allows a small, widely used, pure-JS dependency only when it is the only sane way. It is not.

- **pdfjs-dist** (Mozilla, Apache-2.0, 6.4.299) is the robust choice for rendering, but its package is 35 MB unpacked. It also needs a canvas implementation to render a page to an image in Node, and `node-canvas` is native. Text alone does not need it.
- **unpdf** (MIT, 1.8.1, 2.1 MB) wraps a serverless build of pdf.js. It carries pdf.js's scripting and form layers, which U65 must not run, so it would need configuring that the code here never needs.
- **pdftotext** is on this machine through Homebrew, but macOS does not ship it. The tests use it nowhere. It served only as a reference for the measurement above.
- **PDFKit through `swift` or `osascript`** starts a compiler or an AppleScript host per read and works only on macOS. The fixture script uses it, and the tool does not.

The minimal parser covers what text extraction needs, runs on every platform the engine runs on, and has no surface for embedded scripts.

## Tests

`packages/engine/test/read-documents.test.ts`, 12 tests:

- A Chrome-printed 2-page PDF (Type0 fonts with ToUnicode, a ligature under ActualText) read whole and by `pages: "2"`. A Quartz PDF (TrueType, MacRoman) by `"1"`, `"1-2"` and `"1-30"`, which clamps to its 2 pages.
- A PDF whose pages sit in a compressed object stream.
- 25 pages: the default 10, the continuation hint, `"1-21"` refused, `"21-"`, a page past the end, and a malformed range.
- A JavaScript OpenAction and a form field leave only the page text.
- A 2-page scan: page 1 a JPEG, page 2 raw pixels made into a PNG, both 400x200 and stored as attachments.
- 10 scanned pages: 8 images, and pages 9 and 10 named as left out.
- An encrypted PDF, a truncated PDF and a text file named `.pdf`, each with its error.
- A 64 MB plus one byte sparse file over the size cap, and text over 20,000 characters stopping at a page boundary.
- A notebook with markdown, code, stdout, a text result, a PNG output, a widget and an error. The widget's view and its saved state in the notebook metadata are both absent from the reply.
- `cells: "5"`, a 10,000-character output cut to 4,000, `start_line` reading raw JSON, and a broken notebook.

`packages/engine/test/fixtures/read/make.sh` rebuilds the binary fixtures on macOS from `report.html` with Chrome and `make.swift` with Quartz and PDFKit. `packages/engine/test/pdf-builder.ts` writes the synthetic PDFs inside the tests.

## Live smoke

`pnpm tsx packages/engine/test/read-documents-smoke.ts` copies `report.pdf` into a temp workspace and asks `qwen3.8-flash` on Model Studio how many pages it has, how many units revenue grew to, and what heading starts its last page.

Run on 2026-10-07, it passed in one read call: "It has 2 pages; revenue grew to 4,210 units, and the last page starts with the heading "Appendix"." It cost $0.0012. Three earlier runs while the smoke was built cost $0.0066 together, so U65 spent about $0.008 on the model.

- The first run asked for `pages: "1-30"` of a 2-page PDF, and read refused it as more than 20 pages. Read now counts a range after clamping it to the file, so that read returns both pages.
- Two runs asked for the appendix's "launch code word". The tool result held `The launch code word is PELICAN-42.`, as the session log shows. The model still made up other text once, and once claimed the page held a redacted secret and an exfiltration URL. The smoke now asks about content that does not read as a secret.
