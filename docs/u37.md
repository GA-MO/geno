# U37: widgets in the chat

The model can draw a widget inline in the chat: an HTML, CSS and JavaScript fragment the user sees and can use at once, such as a chart, a mockup or an interactive explainer. It is the `show_widget` tool. It changes nothing on disk, so every interactive mode offers it, Plan included; a non-interactive run, with nobody watching, never sees it.

## The tool

`show_widget` takes `{ title, html, loading_messages? }`. `packages/core/src/widget.ts` owns the shape:

- `parseShowWidget` validates the input and words every rejection for the model. The title is at most 80 characters, the html at most 200,000, and `loading_messages` is up to four short lines.
- `SHOW_WIDGET_SPEC` is the tool the model reads. Its description names the theme variables and the chart palette, asks for `width: 100%` with no fixed container width, and asks for the order style, then markup, then script. The two weak spots the probe found, a fixed 680 px width and off-palette colors, are addressed in the prompt.
- `widgetDraftOf` reads a partial input as it streams, taking only the fields before `html`, so the fragment can never pose as the title or a loading line.
- `WIDGET_PALETTE` is six series colors that each read at 3:1 on both dark glass (`#1e1e20`) and light glass (`#f5f5f5`), with adjacent pairs apart under color blindness. Validated with the `dataviz` skill's checker.

The engine stores the fragment once by its SHA-256 in the session's attachments folder (`$GCODE_HOME/sessions/<id>/attachments/<sha256>.html`) and the tool result logs a `WidgetRef` (`sha256`, `title`, `bytes`), so a loaded session draws it again. `packages/engine/src/tools/widget.ts` is the executor; `storeWidget`, `readWidget` and `loadWidgets` in `attachments.ts` own the store.

## The data shapes

- **Tool input:** `ShowWidgetInput = { title, html, loadingMessages }` (`packages/core/src/widget.ts`).
- **Stored reference:** `WidgetRef = { sha256, title, bytes }`, carried on a `tool-result` event and in a `tool_call_update`'s `_meta` under `gcode/widget`.
- **Draft:** `WidgetDraft = { title?, loadingMessages }`, streamed in a `tool_call`'s `_meta` under `gcode/widget-draft`.
- **Frame builder input:** `FrameInput = { html, nonce, theme }`, and `WidgetTheme = { scheme, vars }` (`packages/core/src/widget-frame.ts`).
- **Panel view:** `ToolWidget`, a union of `drafting | ready | missing` on a tool block (`packages/extension/src/chat/messages.ts`).

## Rendering and the sandbox

A widget draws in a sandboxed iframe. The frame builder is pure, so the chat panel, the widget's editor tab, the download and a unit test all build the same document.

- The iframe is `sandbox="allow-scripts"`, never `allow-same-origin`, so its origin is opaque: no storage, no access to the panel, VS Code, files or Geno, and no forms, popups or top navigation.
- A VS Code webview's iframes inherit the webview's CSP. A `srcdoc`, `data:` or `blob:` frame keeps the panel's nonce-only `script-src`, measured in VS Code 1.109.2 and the `^1.95` engine range. The widget's text never reaches the frame's parser. It travels as a JavaScript string inside one bootstrap script (with every `<` escaped), which parses it inert, gives its scripts and styles the panel's nonce, turns `on*` attributes into `addEventListener` calls, and inserts it.
- The frame's own CSP has no network: `default-src 'none'`, inline styles only, `img-src data:`, no `connect-src`, no `form-action`, no `frame-src`.
- WebRTC is the one escape no CSP covers, so the bootstrap deletes `RTCPeerConnection` before any widget script runs.
- The only channel back is a `postMessage`, validated by the parent for the right source window, a numeric height (clamped 24 to 2400 px), a web link, and a markup snapshot. `fromWidget` in `widget-frame.ts` is the validator.
- A link click becomes a question under the widget. Only the user's "Open" reaches the extension, which opens it in the browser; a link the widget sends on its own, without a click in the frame, raises nothing.

## What the user sees

- While the model writes the widget, the step shows its title, a loading line, and the working dino's pencil pose (U18b).
- The widget draws in a frame sized to its content, in the current glass theme's variables; a theme change restyles the frame in place without loading it again.
- A `⋯` menu offers Copy as Image (the frame's markup is rendered to PNG in the extension host, onto the theme background), Save as Page (since U66: one HTML file in `geno-pages/` with both color schemes, the widget in the same sandboxed frame and the same no-network policy; `docs/u66.md`), and Open in Editor (a read-only webview tab).
- A compact turn folds its work but keeps the widget in view.

## Where it lives

- `packages/core/src/widget.ts`: the tool, the shapes, the prompt and the palette.
- `packages/core/src/widget-frame.ts` (pure): the frame document, its policy and the messages a frame may send. U66's shared page builds the same frame.
- `packages/engine/src/tools/widget.ts`, `attachments.ts`, `session-replay.ts`, `serve.ts`, `agent.ts`: the executor, the store, and the capability and replay wiring.
- `packages/extension/src/chat/widget-model.ts` (pure), `widget-view.ts`, `widget-host.ts`, `widget-tab-view.ts`, `widget.css`.
- Unit tests: `packages/core/test/widget.test.ts`, `packages/core/test/widget-frame.test.ts`, `packages/extension/test/widget-model.test.ts`.
- Engine e2e: `packages/engine/test/widget-serve.e2e.test.ts`.

## Security

`widget-security.integration.test.ts` mounts a widget per attack and proves each is blocked, then shows it getting out against a weakened sandbox. The frame's CSP stops `fetch`, a remote `img` and a `form` post (turn the CSP off and they reach the recording server). The sandbox's opaque origin stops `parent.document` and `localStorage` (remove the sandbox attribute and both touch the panel). The bootstrap's guard stops WebRTC (a frame without the guard, in the same real sandbox, leaks a STUN packet). Top navigation and `window.open` are blocked in depth: the sandbox omits `allow-top-navigation` and `allow-popups`, and the VS Code webview host also refuses both for every frame it hosts, so they stay blocked even once the sandbox attribute is removed.
