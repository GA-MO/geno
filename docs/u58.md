# U58: chapters in long chats

A long session used to be one scroll of turns. Now the agent marks a chapter where the work moves to a different phase, such as from exploring the code to changing it, or from changing it to verifying it. It calls `mark_chapter { title, summary? }`, as Claude Code's agent calls `mark_chapter`. The user can mark one too, from a message's menu. The transcript shows a thin divider with the title where each chapter starts. A small button at the transcript's top left, beside the stuck request, opens a table of contents. Clicking a row scrolls to that chapter, and the row of the chapter being read is marked while the chat scrolls. A session with no chapters shows no button. The brief is the U58 row in the table at the end of [plan-u19-on.md](plan-u19-on.md).

## Data shape

`packages/core/src/chapters.ts` names it. It holds only types and pure functions, so the webview bundles it through the `@g-code/core/chapters` export.

- **The mark.** `ChapterMark` is `{ title, summary? }`. A title is a short noun phrase of at most 40 characters (`CHAPTER_LIMITS.title`), and a summary is one line of at most 200. `parseChapterMark` trims both, puts the summary on one line, drops a blank summary, and refuses unknown fields, in words the model can act on. The engine, the extension and the method's handler all parse with it.
- **The agent's chapter** rides on its call's result, as a todo list (U56) and a spin-off offer (U48) do. A `tool-result` event of `mark_chapter` carries `chapter: ChapterMark`. A cut, a fork and a replay so treat the chapter as they treat the call, with no rule of their own.
- **The user's chapter** is an event of its own, because no tool call makes it. `ChapterEvent` is `{ kind: 'chapter', at, turnSeq, mark }`. `turnSeq` is the seq of the message the chapter starts at, which the panel names a turn by (U50). `mark: null` removes it, and the latest event for a message wins, so a rename is one more event. Like a spin-off decision, it is logged at once, beside a running turn or between turns, with no seq. It is not part of the conversation (`IN_CONVERSATION`), costs no context tokens (`EVENT_TOKENS`), and the model never reads it.
- **The chapter list.** `Chapter` is a mark and its `start`, `{ kind: 'call', toolUseId }` or `{ kind: 'turn', turnSeq }`. `chaptersOf(events)` folds a session's cut view into its chapters in transcript order: an agent's chapter at its result, a user's at its message. It leaves out a refused call and a user's mark at a seq that starts no turn, such as a steer's.
- **The rules.** `newChapterOf(mark, chapters)` refuses a chapter with the title of the one the session is in now, whatever its case. A repeat is the commonest misuse, and the refusal tells the model to mark the next one only when the phase changes. `CHAPTER_MODES` offers the tool in Plan, Ask and Auto, not to a non-interactive run, which nobody navigates.

### Rewind, fork and compaction

| What happens | The agent's chapter | The user's chapter |
| --- | --- | --- |
| A rewind cuts the turn it is in | Gone, with the call's result | Gone. `KEPT_BY_CUT` keeps the event, since it is logged after the turn, but `chaptersOf` leaves out a mark whose message the cut dropped. |
| A rewind cuts a later turn | Stays | Stays, even when it was marked after the cut turns |
| A fork | Copied with its turn | `forkEvents` copies the marks on the turns it takes, though they were logged after them |
| A compaction | Stays in the transcript, which reads the whole log. The model no longer reads the call, so `Kept.chapters` keeps the agent's titles, and the compacted text says "Chapters you marked, oldest first; the session is in the last one: Parser fix \| Test verification". A second compaction carries them on. | Stays. The model never read it. |

A compaction of a session without chapters keeps no `chapters` field, so its text and its log line read as before U58.

## The tool

- **When it is offered.** `chapterToolDefinitions(mode, attached)` gives `mark_chapter` in Plan, Ask and Auto to a client that advertises `gcode/chapters` (`CHAPTER_CAPABILITY`). The VS Code panel does. The terminal, a non-interactive run and a subagent get none, because nobody would see the chapters.
- **No approval.** It never asks, in any mode, Plan included. It changes no file and starts nothing.
- **When to use it.** The description names the phases: exploration done and implementation starting, a fix landed and verification starting, the user changing to an unrelated request. It asks for about 3 to 8 chapters in a long session, never one per tool call or small step, and none for the first message, since the session's start is implicit. It gives three example titles.
- **Deferred.** U46's rule keeps in full only what the loop uses nearly every turn, and a chapter is a few times a session. The definition is 1,080 characters, about 309 tokens. The `tool_search` hint is the description's first words, "Mark the start of a new chapter in this session, where the work moves to a different…".
- **The note.** A run that offers the tool adds `CHAPTER_NOTE` after the mode's system prompt, beside U46's and U48's notes. It is one fixed sentence of about 69 tokens that names `mark_chapter`, so the prefix holds across calls. U48's smoke showed that `qwen3.8-flash` rarely loads a deferred tool that no prompt names.
- **The result.** "Chapter "Parser fix" starts here. The user sees it as a divider and in the chapter list. Go on with the work, and mark the next chapter only when the work moves to another phase." A refusal is an error result with the reason. The executor reads the chapters from the session log on disk, so a chapter the user marked beside the running turn counts as the current one.

## In the engine

- `tools/chapters.ts` holds the executor. `drive.ts` copies `chapter` onto the logged result, and `sessions.ts` accepts the field, the event, and `chapters` in a compaction's `kept`.
- `runAgent` offers the tool and the note when `options.chapters` is set, which serve sets from the window's capability.
- `_gcode/chapters/mark { sessionId, turnSeq, mark }` (`CHAPTER_MARK_METHOD`) parses the mark, refuses a seq that starts no turn, and logs the event at once through `logBesideTurn`, as a spin-off decision is logged. A torn tail falls back to the serial queue. A mark equal to the one standing logs nothing. It answers `{ mark }`, and no model is called.
- The panel learns of the agent's chapter from `_meta["gcode/chapter"]` (`CHAPTER_META`) on the call's `tool_call_update`, live and replayed. A replayed message carries the user's chapter under the same key on its `user_message_chunk`.
- `session-replay.ts` titles a replayed call `mark_chapter <title>`, as it is titled live, and counts `chapter` among `LOGGED_AROUND_TURNS`, so a mark logged after a turn does not stretch that turn's time.
- `gcode session show` prints the mark on the result (`chapter: Parser fix (Guard the month index in parseDate.)`) and the user's event (`chapter at turn 7: Release notes, marked by the user`).

## In the panel

`chapter-model.ts` holds the pure part, which the webview bundles: the messages, `tableOf`, `currentEntry` and `defaultTitle`. `chapter-view.ts` draws the divider, the title field and the table of contents. `chapter.css` styles them.

- **The divider.** A `mark_chapter` call that ran draws as its chapter, not as a call (`rail.ts`, step `chapter`). A running or refused call stays a call. The divider is a thin rule with the title in it, as an `h2`, so a screen reader can jump between chapters by heading. The summary is its tooltip. The rail runs on through it without a node. In compact detail it stays in view when the turn folds, and the fold's summary does not count the call. The user's chapter is the same divider above its message, its title starting where the steps' text does.
- **The table of contents.** A round button with a list icon floats at the transcript's top left, in a zero-height row between the header and the transcript, and shows only while the chat has a chapter and the chat is on screen. While it shows, each message's row keeps 30px clear at its left, so the stuck request never runs under the button. The button is 28px wide and ends at 44px, left of the 46px where every step's text starts, so it covers no text at any width. It covers only the rail's line, its dots and Noodle.
- **The list.** The button opens it below itself: the chat's start, then each chapter in order, with its summary under its title. The start is left out when the user's own chapter opens the chat. The current row has an accent edge, `aria-current`, and the button's label and tooltip name it. On a panel 480px wide or more, the list stays open after a choice and while the chat scrolls, so the marked row follows the reading. Below 480px a choice folds it, so it covers nothing. The button or Escape folds it, and Escape returns the keyboard to the button. Arrows, Home and End move between rows. In the glass style the list is the same blurred float as the other menus.
- **The jump.** The agent's divider scrolls to the top below its turn's stuck request, as a revealed turn does (U57). The user's opens its turn, so it lands just below the button. Start scrolls to the top.
- **The current chapter.** On each scroll frame, `currentEntry` takes the last row whose divider has passed the reading line, which is the transcript's scroll padding below its top, where the stuck request ends. At the end of the chat the line is the transcript's bottom, so a short last chapter still becomes current.
- **Marking by hand.** Each message's menu (U50) has a separator and "Mark a chapter here" under Fork from here. A marked message offers "Rename the chapter" and "Remove the chapter" instead. Mark and Rename open a title field under the message, with the message's first line cut at a word to 40 characters, selected. Enter saves, and Escape or Cancel closes it onto the menu button. The menu shows only while no turn runs, in a Geno session, as before. The live mark reaches the transcript as the `chapter` action. A refusal shows under the message.

## Choices made in this unit

- **The agent's chapter on its result, the user's as an event.** The same split as U48's offer and decision. Cut, fork and replay need no rule for the agent's chapter. The user's needed two small ones: `chaptersOf` drops a mark whose message is gone, and a fork copies the marks on its turns.
- **The user's chapter starts at a message, not at a step.** The menu is on the message (U50), and the message is what the user remembers asking. A mark on an answer or a step would need a menu on every step.
- **Deferred, with a note.** The tool costs about 309 tokens in full on every call and is used a few times a session. A note of about 69 tokens says when to reach for it. A model that never loads it marks nothing, which is the same as before U58.
- **Only for a window that draws chapters.** The terminal draws none, so offering the tool there would cost tokens for nothing.
- **A repeat of the current chapter is refused.** The cheapest guard against a model that marks every step. Other overuse, such as 20 chapters, is left to the description.
- **The button is an icon in the rail's gutter.** A first version showed the current chapter's title on the button at 480px and wider. The screenshots showed it over the previous turn's usage line while a request was being pushed off the top, when no stuck request hides the text. The title now shows in the list, the button's label and its tooltip.
- **The list stays open on a wide panel.** It is a table of contents rather than a menu, so the marked row can follow the reading. Below 480px it covers most of the chat, so a choice folds it.
- **The start is a row.** It is where the reading starts before the first chapter, and the row to jump back to the top.

## Deferred

- The user cannot rename or remove the agent's chapter. Its title comes from the model's call, and a rename would need an event that overrides a result.
- A subagent gets no `mark_chapter`, and a child's rail draws no table of contents.
- No live smoke checked that `qwen3.8-flash` marks chapters unprompted, since this unit spent no model money. Run 3 of U48's smoke suggests the note helps a small model reach for a deferred tool, but that is a guess for this tool.
- Two `mark_chapter` calls with the same title in one model response both go through: each reads the log, and the batch's results are logged together after it ends. U48 has the same gap.
- A woken turn has no message, so nothing stops a step's text from scrolling under the button when that turn is at the top. The button covers only the gutter there too, so this is a guess that the sweep did not reach, not a measured case.
