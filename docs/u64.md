# U64: workflows

Before U64, a multi-agent job such as "review, then fix, then verify" meant prompting each step by hand, or trusting the model to start the right subagents in the right order. Arena (U26) ran one fixed shape of that job. Now a workflow is a small JSON file in the workspace that names its steps: subagent calls, steps side by side, a pipeline over a list, and gates. The user starts one with `/workflow <name>`, or the model with the `workflow` tool. Before anything runs, the user sees what each step may spend and the total cap, and confirms. The run goes on in the background as a session of its own, each step one of its subagents, listed in Tasks. Its report comes back to the session that started it as a woken turn (U49). It is the general form of Arena, and Geno's answer to Claude Code's `Workflow` tool. The brief is the U64 row of "More capabilities the coordinator's harness has and Geno lacks" in [plan-u19-on.md](plan-u19-on.md).

## The format: JSON, not a script

Claude Code's `Workflow` tool runs a JavaScript script. U64 uses a declarative JSON file instead.

| | A JS module in a restricted context | Declarative JSON |
| --- | --- | --- |
| Deterministic | Only if the context strips `Date`, `Math.random` and every timer, and the script uses nothing else that varies | By construction: there is nothing to run but the steps |
| Files and network only through agent steps | Node's `vm` is not a security boundary: `this.constructor.constructor('return process')()` reaches the host. A real sandbox is a second process or a WebAssembly interpreter | Nothing in the file can run, so nothing can reach anything |
| Exact cost preview | Needs a dry run of the script with stubbed steps, which can take another branch at run time | A walk over the steps; only a pipeline over an earlier step's list is counted at its `maxItems` |
| Refs checked before a run | No: a typo in a variable shows mid-run, after money is spent | Yes: every `{{step}}` and `{{step.field}}` is checked against earlier steps' schemas when the file loads |
| Expressive | Loops, conditions, anything | Sequence, `parallel`, `pipeline` and gates, which covers review-fix-verify, fan-out reviews and fix-each-finding |

The user is a cost-conscious solo developer. A file that cannot spend money it did not show first matters more to them than loops. A file in a cloned repository is also untrusted input, so "nothing in it runs" is the safety property that needs no review. JSON over YAML because the repository has no YAML parser, and a prompt may be a list of lines, which takes the sting out of multi-line strings in JSON.

## Data shape

`packages/core/src/workflow.ts` names it, with types and pure functions only. `packages/core/src/workflow-progress.ts` holds the part the webview bundles, as `@g-code/core/workflow-progress`.

- **The file.** `.g-code/workflows/<name>.json` in the workspace, or `~/.g-code/workflows/<name>.json`. A workspace file shadows a global one of the same name. The name is the file's base name: lowercase letters, digits, `-` and `_`. The top level is `{ description, input?, maxCostUsd?, steps }`. `input` says what the text after the name means. `maxCostUsd` is the run's total cap, $0.50 by default and $5 at most.
- **Steps.** `WorkflowNode` is one of four:

  | In the file | Node | Runs |
  | --- | --- | --- |
  | `{ "role", "prompt", "id"?, "model"?, "lane"?, "maxCostUsd"?, "maxTurns"?, "schema"? }` | `agent` | One subagent of that role. The caps replace the role's; the model replaces the session's. `lane` is read and refused for now (see Deferred). |
  | `{ "parallel": [agent steps] }` | `parallel` | 2 to 8 agent steps in one round. |
  | `{ "pipeline": { "items", "maxItems"?, "stages" } }` | `pipeline` | Each item through every stage in turn; one stage runs for all items in one round. `items` is a list of lines, or `"<step>.<field>"` naming a `string[]` field of an earlier step, cut at `maxItems` (5 by default, 10 at most). |
  | `{ "gate": "check" }` or `{ "gate": { "field": "<step>.<field>", "equals": <value> } }` | `gate` | The project's check, or a test on an earlier step's field. A gate that fails stops the run. |

  A step without an `id` takes its role's name, then `<role>-2`, and so on.
- **Templates.** A prompt holds `{{input}}`, `{{<step>}}` (that step's fenced report), `{{<step>.<field>}}` (a field of its JSON, as text), and, in a pipeline's stages, `{{item}}` and `{{previous}}` (the item's report from the stage before). A parallel's or a pipeline's own id names all its reports, joined. `parseWorkflow` checks every ref against the steps before it and their schemas, so a typo is a load error with the step's number, never a mid-run surprise.
- **Schemas.** `schema` is `{ field: "string" | "number" | "boolean" | "string[]" }`. The step's task gets a line asking for one JSON block of that shape, and `readFields` takes the last block in the report with every field of the right type. A report without one fails the step.
- **Limits.** `WORKFLOW_LIMITS`: a step's cap at most $1 and 100 model calls, 40 calls and checks in a run with every pipeline at its most items, 20,000 characters a prompt.

### The run

`WorkflowRun` is `{ spec, input, status, stop, at: { node, stage }, items, outputs, units }`. A unit is one agent call or check the run issued, numbered from 1, with its status, cost, model calls, child session and a note. Two pure steps move it:

- `nextRound(run, agents)` gives the calls of the next round once every unit before them settled, or ends the run. It evaluates field gates on the way, since they need no call, and skips a pipeline whose list is empty.
- `settleUnit(run, index, outcome)` records one unit. Once its round settles, the run moves on, or stops.

| A unit ends | The run |
| --- | --- |
| `done`, with its schema's block when it has one | moves on once the round settles |
| `done`, without its schema's block | stops: `step-failed` |
| `capped` at its turns or cost | stops: `step-cap` |
| `failed` | stops: `step-failed` |
| `cancelled` | is cancelled |
| A check that passed | moves on |
| A check that failed, or a workspace with no check command | stops: `gate` |
| A field gate whose value differs | stops: `gate`, with no call |

A round runs to its end before the run stops, so a failed branch never leaves a sibling running unheard. The first stop in issue order is the one the report names. `cancelWorkflow` cancels what still runs.

### The cap rule

**A round starts only when what the total cap has left covers every one of its calls' cost caps in full.** Otherwise the run stops before it with `total-cap`, which names the step, what its caps need and what is left. So no step ever gets less than its stated cap, and the run can never pass the total, whatever the steps do. What is left is the cap less what the settled units spent, so a run whose early steps spent little goes further than the preview's worst case. The subagent engine holds the same line: the workflow session's cost limit is the total cap, and each child reserves its cap from it when it starts (U22).

### The cost preview

`workflowPreview(spec, input, agents, { model, rates })` gives a `PreviewRow` per step and gate, and the totals:

- A step's caps are its own, else its role's, else a child's defaults, $0.05 and 20 model calls (`stepCaps`).
- A step's estimate is its model's price for `ESTIMATE_CALLS` (6) calls of `ESTIMATE_CALL` tokens (7,000 in, 400 out, about Geno's first request with tools and a short answer), held to its cost cap and to its turn cap. On `qwen3.8-flash` that is $0.0074 a step.
- `estimateUsd` sums the estimates, `worstUsd` sums every step at its cost cap, and `stopsBefore` names the first step the total cap would stop before were every step to spend its whole cap. A pipeline over an earlier list counts at its `maxItems`.
- A model with no price gives no estimate and is listed in `unpriced`, since its cost caps cannot hold.

`previewQuestion` says it in one line, the card's title: "Run workflow review-fix-verify: 4 steps, about $0.02, at most $0.25 (cap $0.40)?".

### Determinism

A run is a function of the file, its input and what each unit reported. `workflowTurn(calls, model)` makes a round's tool calls with ids `toolu_gcode_wf_<n>`, so the same reports give the same calls, ids, tasks and caps. The unit test runs a whole review-fix-verify twice and compares every issued turn and the end state.

## The tool and the command

- **`/workflow <name> [input]`** is an engine built-in that runs a turn. Its prompt is logged as "Run the workflow <name> <input>", and `runAgent` turns it into the user's own `workflow` call, as `@explore` is the user's own `agent` call, so no model reads it first. `/workflow` with no name lists the workflows, and the files that did not load with their problems.
- **`workflow { name?, input? }`** is the model's tool. Without a name it lists them.

Both go through one executor (`tools/workflow.ts`). It reads the file once (`prepare`), refuses what cannot run here (`workflowRefusal`: a role the session has no agent for, a role on an external agent, `isolation: worktree`, a step with a `lane`, or a role that edits in Plan mode), and asks the user with the preview. The card runs exactly what it showed: a file changed while the card waits does not change the run. "Don't run" starts nothing. A deferred tool's call is refused until `tool_search` loads it (U46), except a call the user issued, so `/workflow` works in a session whose model never loaded the tool.

The tool is offered in Plan, Ask and Auto to a client that advertises `gcode/workflows` (`WORKFLOWS_CAPABILITY`), as the VS Code panel does. A non-interactive run, the terminal and a workflow's own session get none.

## In the engine

- **The director.** `Mode.issued`, one turn the user typed, became `Mode.director`: asked at each point the loop would call the model, it answers with a turn to log as the user's own, or nothing, which ends the run. `issuedOnce(turn)` is the old behaviour, which `@explore` and the Arena's review use. A workflow's director (`workflowDriver` in `packages/engine/src/workflows.ts`) folds the log into the run with `absorbOutcomes`, asks `nextRound`, and issues the round. When the run ends, it issues its report as a text turn, which a viewer of the session sees stream in as a model's text, and the loop ends. The loop runs the rounds as it runs any tool calls: read-only steps of a round side by side, up to 4 at once, and a step that edits alone.
- **Steps are children.** Each agent call is an ordinary `agent` call of the workflow session, so each step is a subagent with its own session log, its child-start and child-end events, its Tasks row under the workflow's, and its transcript in the side view (U23). Calls a director issues may also set `model`, `max_turns` and `max_cost_usd`; a model's call that sets them is refused. A check gate is the agent tools' own `check` call.
- **The run's session.** `runWorkflow` in `serve.ts` starts a background session titled "Workflow <name>" in the starting session's workspace and mode, with `startBackground` (U62), the total cap as its cost limit, and the director. Each change of the run goes to Tasks as `TaskRecord.workflow`, a `WorkflowProgress`, which the record keeps after the turn ends.
- **The report.** When the run's turn ends, `finish` reads the log once more, cancels what is left (or fails it, if the turn ended by itself), and the engine puts the report into the starting session's inbox as a background child's report (U49): `<subagent_report agent="workflow <name>" session=… status=…>`, with what ran, each step's model calls, cost and session, what did not run, and the last step's report. With auto-wake on, that wakes the session, which shows as "woke: 1 task finished"; while the session waits, Tasks says "Wakes on workflow <name>". With it off, the report joins the running turn or the next one.
- **Cancel.** Stop on the workflow's Tasks row cancels its turn, which cancels the running step's child; nothing after it runs, and the report says "was cancelled". The starting session's Cancel (U49) silences the run and stops it, with no report.

## In the panel

- **The card.** "Run this workflow?" shows the name and description, the input, each step on three lines (its id, then its role, model and whether it reads or edits, then "About $0.0074 · up to $0.15 and 20 model calls"), gates as "Gate" and "Gate on a field", and the total: "About $0.02, at most $0.25. The run stops cleanly at its total cap of $0.40." It warns when the total cap would stop the run were every step to spend its cap, and when a model has no price. Settled, it reads "Started, in Tasks" or "Not run". Every text is a text node; at 300px nothing leaves the card.
- **Tasks.** The workflow's row has a line with its own icon: "Step 2 of 4: fix · $0.0002 of $0.40", "Finished 4 steps · …", or "Step 2 of 5: stopped at fix, which hit its cost cap · $0.17 of $0.40". Its steps count as "1 agent running". The row shows no turn cost, since its own turn calls no model, and no Message, since a workflow takes none; its steps do.
- **Where it lives.** `workflow-wire.ts` checks the preview at the boundary, `workflow-view.ts` draws the card's body, `workflow.css` styles it, and `lanes-model.ts` gives the row its line.

## Examples

Two templates live in `docs/workflows/`. Copy one into `.g-code/workflows/` to use it; Geno installs none by itself. A unit test parses both and checks they run in Ask with the built-in roles and fit their own cap.

- [`review-fix-verify.json`](workflows/review-fix-verify.json): `review` lists findings, `worker` fixes them (up to $0.15 and 20 model calls), the project check runs, a second `review` verifies, and a gate holds the run to `verify.pass`. About $0.02 on `qwen3.8-flash`, at most $0.25, cap $0.40.
- [`three-angle-review.json`](workflows/three-angle-review.json): three `review` steps in parallel (security, tests, types), a `plan` step merges them into at most 5 findings, a pipeline has a `worker` fix each finding in turn (up to $0.06 each), and the project check runs. At most $0.50, cap $0.60.

`/workflow review-fix-verify the auth module` runs the first.

## Choices made in this unit

- JSON, not a script (see the table above). Nothing in a workflow file runs, so a file from a cloned repository needs no sandbox, and the preview is a walk, not a guess.
- One path for the user and the model. `/workflow` is the user's own `workflow` call, so both get the same card, the same refusals and the same run.
- The card is a permission card with the preview on it, not a new kind of request, so every client that can answer a permission can answer it.
- A round starts only when the total cap covers its caps in full. A cheaper rule would let a step start with less than its cap; this one keeps every number the card showed true.
- Any failed, capped or cancelled step stops the run, after its round settles. A step that follows usually needs the one before it whole.
- The run is its own background session whose turn a director drives, rather than children of the starting session. Its steps nest under it in Tasks, its log reads as a normal session, and the starting session's own turns stay free.
- Steps that edit side by side run one after another in the main checkout, as the loop runs any edits; the file is not refused.
- A gate that cannot check, in a workspace with no check command, stops the run. A gate that passes without checking would be worse than none.
- The run's progress lives in the engine's memory and in Tasks; its log is the record. A run does not survive the engine: its children die with it, as background children do.

## Deferred

- **`lane` on a step.** The file takes it, but `workflowRefusal` refuses such a workflow before anything runs, since a native child runs in its parent's checkout. Running a child in a lane needs its own sandbox and executors bound to the lane, which is the next step, and with it, parallel writers.
- A check gate checks the main checkout only.
- A workflow's session loaded from History shows its `agent` calls without the children nested under them, as U23 left replays.
- The turn that only issued `/workflow` shows a usage footer of 0 tokens and $0.00.
- The Tasks row's clock is drawn when the row changes, so a running workflow's time can read low until its next step.
- No form makes or edits a workflow; the user writes the JSON file, or asks the model to.
