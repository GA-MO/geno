# U43: "needs you" ordering in the Tasks list

Before U43, the Tasks list put running tasks first and then the rest, newest first. A task that waited on the user sat among the running ones. Now the list has four sections, and the one that waits on the user comes first. The brief is section 2.5 and section 5, item 1, of `research/t3code-2026-10.md`. T3 Code's Working section folds busy threads away and orders the rest by when each last came back to the user. Geno does the same.

## Data shape

`packages/core/src/attention.ts` holds all of it, and it is pure. The webview bundles it through the `@g-code/core/attention` export.

- **Attention.** `Attention` is a discriminated union:
  - `needs-you`, with a `reason` and `at`. The reason is `permission`, `question`, `failed` or `limited`. `at` is the session that shows what to answer.
  - `ready`: the task finished, and the user has not opened it since.
  - `working`: the task runs, or waits for a call that goes out again by itself.
  - `done`: the task ended and the user saw it, or the user stopped it.
- **The task record.** `TaskRecord` gains four optional fields:
  - `asking`: the card a `needs-input` task shows, `permission` or `question`.
  - `parent`: the task this one rolls up into. This is a subagent's parent session, or an Arena lane's run.
  - `kind`: `session`, `subagent` or `arena`. Absent reads as `session`.
  - `returnedAt`: when the task last came back to the user.
- **When a task came back.** `returnedAtOf(before, after, now)` stamps `now` when a task becomes the user's turn, or when its status changes while it is the user's turn. "The user's turn" (`isWithUser`) means the task asks, holds at a limit, or ended. A wait that resumes by itself is still work. The engine's `Tasks` book applies it on every change.
- **Placement.** `placeTask({ task, children, seenAt })` returns the task's `attention`, its `returnedAt` (the latest of the task and its children), and a sort `key`. The key is the section, then the reason's tier within Needs you, then the newest return first. `placeTasks(tasks, seen)` groups children under their parents and sorts. A child whose parent the list no longer holds stands on its own.
- **Seen markers.** `SeenMarkers` maps a session or Arena run id to when the user last opened it. `markSeen` in `packages/extension/src/chat/lanes-model.ts` moves a marker only forward and keeps the newest 200. `seen.ts` keeps them in `seen.json` in the extension's workspace storage, for the reason `sessionMemory` gives: VS Code keeps `workspaceState` in memory under extension tests, so a reload test could not read it back.

### Section rules

A task's own state, before its children:

| Task | Seen since it came back | Section |
| --- | --- | --- |
| `needs-input` with a permission card | either | Needs you, permission |
| `needs-input` with an ask_user question | either | Needs you, question |
| `failed` | no | Needs you, failed |
| `failed` | yes | Done |
| `waiting`, held for Retry now (`retryAt` null) | either | Needs you, limited |
| `waiting`, resumes by itself | either | Working |
| `running` | either | Working |
| `done` | no | Ready |
| `done` | yes | Done |
| `stopped` | either | Done |

Within Needs you, permission and question share the first tier, then failed, then limited. Within every section, the newest return comes first.

### Child roll-up

Only a live child rolls up. A child that asks, or holds at a limit, puts its parent in Needs you. A child that runs keeps a finished parent Working. A child that ended says nothing, since the parent goes on with the outcome. The most urgent state wins, in this order: the Needs you tiers, Working, Ready, Done.

A subagent asks on its parent's card, so `at` is the parent. An Arena lane asks in its own session, so `at` is the lane.

## Engine

- `Tasks.ask(sessionId, card)` names the card. `askEditor` passes `permission` for a command or a memory card and `question` for ask_user. A subagent's permission goes on the subagent's own task, by the `asker` the approval already carries.
- `acpChildHost` takes a `tasks` hook. Each child starts a task with `kind: 'subagent'` and its parent's id, titled with its role and the first line of its task. Its end maps `done`, `failed`, `cancelled` and `capped` to `done`, `failed`, `stopped` and `done`. The book drops an ended subagent's task right after it tells the end, because the parent's own task holds the outcome.
- An Arena run is a task of its own, `kind: 'arena'`, titled "Best of N: task". It starts with its first lane and ends as the run settles: `ranked` is `done`, `no-winner` is `failed`, and `stopped` is `stopped`. `LaneRunner` gets the run id, and `Tasks.adopt` binds each lane's session to the run before its turn starts.
- `Tasks.end` ends a task once. A later end changes nothing.
- The book keeps the newest 20 ended top-level tasks, and a dropped task's children go with it.

## In the panel

- **Sections.** The Tasks pane shows Needs you, Ready, Working and Done, each with its count, and leaves an empty one out. A row in Needs you has an amber edge and says what to do: "Needs permission", "Needs your answer", "Failed", or the wait's words. A Ready row keeps its status badge and adds a New pill. A row with children says "1 agent running" or "3 lanes". Subagents and lanes get no rows of their own.
- **Working** folds to one line by default: a chevron, "Working", the count, and the titles, cut with an ellipsis. A click opens it. The rows stay in the DOM while folded.
- **Done** shows its newest 5, and "Show N more" shows the rest.
- **Open.** A click anywhere on a row, or its Open button, opens the task at what it needs:
  - a card: the session loads, and the card takes the keyboard and scrolls into view;
  - a held limit: Retry now takes the keyboard;
  - a failure or a finish: the end of the transcript;
  - an Arena run: the Arena pane on that run.

  A loaded session's card arrives after the replay, so the webview keeps the request for 5 seconds until it finds the card.
- **Seen.** The chat in view, in a window in front, marks its session seen as it changes. The Arena pane marks each run it shows. A marker moves only past a change it has not seen, so the file is written once per change, not on every usage update.
- **Notices.** The extension now decides them from the move between sections, not from the engine's status table. A move into Needs you tells VS Code and, when the window is not in front, macOS. A move from Working to Ready tells VS Code only. Working never notifies. The engine's `missed` notices name the task, and the extension tells them by the task's section now. A held limit now notifies, since it needs the user.

## Where the needs-you count lives

On the view's badge, the number on Geno's icon in the activity bar, or on its tab in another container. Before U43 it counted the tasks running in the background. Its tooltip reads "1 task needs you" or "N tasks need you".

I chose it over the composer's running row and the panel's title:

- It shows while the panel is closed or another view is in front, which is when the user most needs to know.
- It takes no room in the webview, so the 300px running row keeps the room U23 and U42 measured for it.
- The running row shows only while the shown chat runs, so it would hide the count the rest of the time.
- The view's title already holds the session's cost (`totalsLabel`).

## Choices made in this unit

- A failed task leaves Needs you once the user opens it. Otherwise a failure would stay there for good.
- Seen decides Ready against Done for every kind of task. A lane done and not applied, or an Arena ranked and not picked, is Done once opened.
- A permission card or a question stays in Needs you after the user looked at it, since it still waits.
- Only a held limit is Needs you. An offline wait, or a limit that resumes by itself, is Working.
- An Arena run with no passing lane counts as failed, so it shows in Needs you.
- A finish still raises VS Code's notification, as U25's lanes test asserts, but never the macOS one.
- Subagents get tasks of their own in the engine, so the roll-up has the same shape for subagents and lanes. Their tasks are dropped once they end.
- The seen markers live in the extension, in a file per workspace, not in the engine, because the engine's task list ends with its process.

## Deferred

- Two windows of one folder each keep their own copy of the seen markers and write the file in turn, so one window can miss what the other saw.
- Snooze and auto-settle, which T3 Code has. A solo user with a handful of sessions does not need them yet.
- The composer's agents pill still counts running children. It does not show the needs-you count.
