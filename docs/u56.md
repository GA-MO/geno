# U56: a live todo list

The model keeps a checklist of the task's steps with a `todo` tool. The panel pins the list above the running turn's latest step, so a long task shows what is done and what is left at a glance. The brief is the U56 row in the table "More capabilities the coordinator's harness has and Geno lacks" at the end of `docs/plan-u19-on.md`.

## Data shape

`packages/core/src/todo.ts` holds all of it. It imports only types, so the webview bundles it through the `@g-code/core/todo` export.

- **The item.** `TodoItem` is `{ id, text, status }`. `TodoStatus` is `pending`, `in_progress` or `done`.
- **The list.** `TodoList` is a readonly array of items. Each call sets the whole list, so there is no patch format to get wrong.
- **The rules.** `parseTodo(raw)` returns the list or a problem the model can act on. It refuses more than 30 items, more than one item in progress, an id used twice, an empty id or text, text over 200 characters, and an unknown status or field. An empty list clears the list.
- **The event.** `TodoEvent` is a `tool-result` event that carries `todo: TodoList`. The call's own result in the session log is the event, as a widget's result carries its widget. `isTodoEvent` picks it out.
- **The reducer.** `reduceTodo(list, event)` returns the event's list for a todo event and the list unchanged for any other event. `todoOf(events)` folds a session's events. A refused call logs no list, so it changes nothing.
- **Words.** `todoLine(list)` is the folded row's text, such as "1 of 3 done · write tests". `todoResult(list)` is what the model reads back.

Rewind and fork need no code of their own. `readSessionLog` applies `cutView`, which drops a cut turn's tool results, so `todoOf` gives the list as it stood before that turn. `forkEvents` copies the tool results of the turns it takes, so a fork starts with the list as it stood after the turn it forked at.

## In the engine

- `todo` is in `AGENT_TOOL_NAMES`, so every mode offers it. Plan offers it too, since `PLAN_LEAVES_OUT` does not name it. `CHILD_TOOL_NAMES` leaves it out, because a subagent's list would show nowhere.
- The Plan prompt gains one sentence after its bullet list: "Also write the steps with the todo tool, all pending, since that same list is the one you tick off once the user starts building." No other prompt changes.
- `tools/todo.ts` parses the input by core's rules and returns `{ text, todo }`. `drive.ts` puts `todo` on the tool-result event, and `sessions.ts` accepts it in the log schema.
- The panel gets the list under `_meta["gcode/todo"]` as `{ items }`, in two places. `toolEnd` sends it as soon as the call ends. `toolResultUpdate` sends it again with the result, live and in a replay. The first matters because a batch's results are logged only after every call in it ends: a todo call beside a long `bash` command would otherwise show its list only when the command ended.
- A replayed todo call is titled "todo 1 of 3 done · write tests", as it is live.

## In the panel

- **Where it stands.** `railOf(turn, carried)` in `rail.ts` adds a `todo` step and draws no todo call as a call. A call the engine refused stays a failed call.
  - In a running turn, the list is pinned just above the latest step, including the thinking step. It moves down as steps arrive.
  - A running turn pins the list it set. Before its first call, it pins the list an earlier turn left, if that list has work left. This is how Start building shows Plan's list at once.
  - Once the turn ends, the list stays where the turn last changed it, and earlier versions are not drawn.
- **The fold.** The head is one line: a checklist icon, "3 of 7 done · writing tests", and a chevron. A click folds or opens the list. Pinned, the list starts open, because it is the turn's progress. Kept in the transcript, it starts folded. Each has its own id in the view's open list, so folding the pinned list does not decide how the kept list starts.
- **Items.** A pending item has an empty circle. The item in progress has a spinner and bold text. A done item has a green check and is dimmed to 55%. High contrast does not dim: a done item keeps full strength with a line through it. Reduced motion stops the spinner.
- **Compact detail.** A todo step always stays in view, as a widget does, and does not take one of the four recent-step places. The fold's summary does not count todo calls.
- **The composer label.** When nothing needs the user, the U43 label names the item in progress, such as "Write tests", before the latest step. It shows only while the pill shows, as before.
- **Width.** The head's line cuts with an ellipsis. Item text wraps. At 300px, nothing leaves the transcript and nothing scrolls sideways.

`todo-model.ts` reads the list from an update for `chat.ts`. `todo-view.ts` draws the step, and `todo.css` styles it.

A fork at each turn copies the list as it stood. The tests also check that Plan offers the tool and a subagent does not, and that only Plan's prompt asks for the list.
- `packages/engine/test/todo.e2e.test.ts` runs serve with a fake model. A Plan-like turn sets three pending items. A second turn sets two more lists. Each call's list arrives live. A new engine process on the same store (a reload) replays all three. A fork at turn 2 has turn 2's list, replays it, and its next request carries the three calls. A conversation rewind of turn 2 takes the source back to the plan's list, while the fork keeps its copy. The replay shows only the plan. The next request carries only the plan's call.
- `packages/extension/test/todo.test.ts` covers the rail: the pinned list above the latest step, above the thinking step, kept where it last changed, the carried plan pinned before any call, a finished earlier list not pinned, a refused call shown as a call, and a cleared list shown as nothing. It also covers compact detail, the summary, reading the list from an update with the rules applied, and the composer label.
- `packages/extension/test/todo.integration.test.ts` runs the real engine against a fake model in VS Code. The user picks Plan and sends the prompt. The first request offers `todo` and no `edit`. The Plan turn ends with its list folded to "0 of 3 done" before the answer. Start building pins the same three pending items, open, before the model answers. The next request carries the plan's call. The done item is dimmed, and only the item in progress spins. A click folds the list to one line under 40px high, and another click opens it. At 300px the list fits with no sideways scroll. When the turn ends, the list stays before the answer as "3 of 3 done", folded, and opens on a click.

## Live smoke

`pnpm tsx packages/engine/test/todo-smoke.ts` gives `qwen3.8-flash` on Model Studio a temp workspace with `math.ts`. It asks the model to track three steps with the todo tool: add `sub`, add `mul`, then read the file back and count the exports. It passes when every list the panel received has 3 items, there are at least two lists, the last list is all done, and `math.ts` has both exports.

The run on 2026-10-07 passed with three lists: "0 of 3 done · add `sub` export to math.ts", then "1 of 3 done · add `mul` export to math.ts", then "3 of 3 done". It cost $0.0087. An earlier run, whose prompt said only "tracked in your todo list", cost $0.0055 and never called the tool, so U56 spent $0.014 on the model.

## Choices made in this unit

- The list lives on the call's tool result, not in a new event kind. The cut, the fork, the replay and the log schema already handle tool results, so rewind and fork reproduce the list with no new rule.
- Each call sets the whole list. A replay is the last list, and a refused call cannot leave half an update.
- The Start building turn pins the previous turn's list only when that list has work left. A finished list from an earlier turn is history, not progress.
- The kept list folds by default and the pinned one opens by default. The running list is the progress to watch, and a finished turn's list is a record.
- Subagents get no todo tool.

## Deferred

- `qwen3.8-flash` did not use the tool unless the user's message named it. The tool's description says to use it for three or more steps, and Plan's prompt asks for it, but the main system prompt's line that lists the tools does not name `todo`. That line was left as it was, to keep the prompt's bytes stable. Naming the tool there is the next step if unprompted use matters.
- A subagent keeps no list. A long child task shows its steps only in its own transcript.
- The pinned list scrolls with the transcript. It does not stick to the bottom of the panel while the user reads further up.
