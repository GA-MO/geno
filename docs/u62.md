# U62: scheduled tasks

Before U62, Geno ran only while the user was there to send a prompt. U49's `schedule_wakeup` woke the same session once, within an hour. Now a task can run by itself later, once or on a schedule, such as "every weekday at 9:00 run /review on main" or "in one hour, check the deploy". The engine keeps the tasks per workspace in its home, so they outlive it. Each run is a new background session with its own budget, listed in Tasks like any other. The user makes a task with `/schedule` in the chat, and the model makes one with `schedule_task` after the user approves it. The brief is the U62 row of "More capabilities the coordinator's harness has and Geno lacks" in [plan-u19-on.md](plan-u19-on.md).

## Data shape

`packages/core/src/cron.ts` and `packages/core/src/schedule.ts` name it. Both hold only types and pure functions, with the time zone passed in, so tests pin it. The webview bundles them as `@g-code/core/cron` and `@g-code/core/schedule`.

- **The schedule.** `When` is `{ kind: 'cron', expr }` or `{ kind: 'at', at }`. A cron is five fields (minute, hour, day, month, weekday) or a macro such as `@daily`. `parseCron` reads `*`, numbers, ranges, lists, steps, month and weekday names, and 7 as Sunday. When both the day of the month and the weekday are given, a day matches either, as Vixie cron does.
- **Local time.** `nextCronAfter(cron, after, zone)` gives the first instant after `after` that the cron names in `zone`. `instantOf(wall, zone)` turns a wall-clock minute into an instant, by the rules Temporal calls `compatible`:

  | The clock | A daily 02:30 in New York | Rule |
  | --- | --- | --- |
  | goes forward (8 March 2026, 02:00 to 03:00) | runs once, at 03:30 | a minute the clock skips moves later by the hour skipped |
  | goes back (1 November 2026, 02:00 to 01:00) | a daily 01:30 runs once, at the first 01:30 | a minute the clock shows twice is its first showing |

  An hourly task runs once an hour across both changes. A schedule with no run in five years, such as February 30, never runs, and `/schedule` refuses it.
- **The task.** `ScheduledTask` is `{ id, title, prompt, when, edits, budget, paused, createdAt, createdBy, since, runs }`.
  - `id` is `sch_` and 6 hex digits, short enough for the model to copy back.
  - `edits` false runs each session in Plan, in the main checkout, which is read-only. True runs it in its own lane (U24), in Auto.
  - `budget` is `{ maxCostUsd, maxTurns }`. `DEFAULT_SCHEDULE_BUDGET` is $0.05 and 20 model calls, and `SCHEDULE_LIMITS` caps them at $1 and 100.
  - `createdBy` is the user, or the model with its session id.
  - `since` is the cursor. Occurrences at or before it are settled, run or missed. It starts at the creation time. A resume or a new schedule moves it to that moment, so neither runs what came due before.
  - `runs` keeps the newest 10.
- **A run.** `ScheduleRun` is one of three:
  - `ran` `{ dueAt, trigger, startedAt, sessionId, workspace, lane, by, end }`. `trigger` is `schedule`, `catch-up` (more than a minute late) or `now` (the user's Run now). `by` is the engine's pid. `end` is null while the run goes on, then `{ kind, at, costUsd, message }`, with `kind` one of `done`, `failed`, `stopped`, `budget` and `max-turns`. `runEndOf(events)` reads it from the session's log: its last error decides.
  - `missed` `{ from, to, count, why }`. `why` is `off` (Geno was not running) or `busy` (the last run still ran).
  - `not-started` `{ message }`: the session could not start, such as an edit task in a folder that is not a git repository.
- **The missed-run rule.** `planDue(task, now, zone, policy, busy)` says what a task needs now. It is a table, first match wins:

  | The task | Plan |
  | --- | --- |
  | Paused, or no occurrence left | `none` |
  | No occurrence due since `since` | `wait` until the next |
  | Its last run still runs | `miss` everything due, `busy` |
  | The latest due occurrence is more than the grace window old | `miss` everything due, `off` |
  | Otherwise | `run` the latest due occurrence once, and record the earlier ones as `skipped` |

  `SCHEDULE_POLICY.graceMs` is one hour. So a 9:00 review runs at 9:40 if the Mac woke then, and is recorded as missed if it woke at 10:30. A task off for days runs once, not once per day. Counting stops at 999, so a minutely task off for a month costs a few searches, not 40,000.

## Making a task

- **`/schedule`** is an engine built-in: `/schedule <when> [--edits] [--max-cost <usd>] [--max-turns <n>] <prompt>`. `when` is one of:

  | Form | Means |
  | --- | --- |
  | `in 1h`, `in 30m`, `in 1h30m`, `in 2 days` | once, that long from now |
  | `at 9:00`, `at 9pm` | once, the next time the clock reads it |
  | `at 2026-10-08 09:00` | once, then |
  | `daily at 18:30`, `every day at 7am` | `30 18 * * *`, `0 7 * * *` |
  | `weekdays at 9:00`, `every weekday at 9:00` | `0 9 * * 1-5` |
  | `0 9 * * 1-5`, `cron "*/15 9-17 * * 1-5"`, `@hourly` | that cron |

  The flags come between the time and the prompt, so the prompt can say anything, `--edits` included. The prompt may be a slash command such as `/review main`; the run expands it as it would a typed one. The title is the prompt's start. `/schedule` with nothing after it prints the usage and the workspace's tasks. It calls no model and asks nothing, since the user typed it.
- **`schedule_task`** takes `{ action, id, title, prompt, when, edits, max_cost_usd, max_turns, paused }`, with `action` one of `create`, `list`, `update` and `delete`. `when` takes the same forms. An update changes only the fields it names, budget limits included. `parseScheduleTask` gives every refusal in words the model can act on.

### Approval

A run spends money with nobody watching, so every create, update and delete asks the user, in every mode the tool is offered in. Auto never sends it to the classifier, as it never sends `remember`. The card reads, for example, "Schedule "Review main": Weekdays at 09:00 (next Thu 8 Oct 09:00), read-only, up to $0.05 and 20 model calls a run?", with the reason "A scheduled task runs by itself, with nobody watching, and each run spends up to its budget." Its options are Allow, "Allow schedule changes in this chat" and "Don't allow". The second is the pre-approval: the engine keeps it for the session while it runs. `list` asks nothing.

### Where it is offered

`scheduleToolDefinitions(mode, attached)` offers the tool in Plan, Ask and Auto, and only to a client that advertises `gcode/schedules` (`SCHEDULES_CAPABILITY`). The VS Code panel does. A non-interactive run and the terminal get none. A scheduled run's own session gets none either, so a run cannot schedule more. The tool is not a core tool, so U46's roster defers it. Its definition is about 560 tokens by the roster's estimate, so deferring it saves that much more in every editor mode:

| Client and mode | Saved before U62 | Saved now |
| --- | --- | --- |
| An editor without `remember` or the widget, Plan | 1,620 | 2,182 |
| An editor without `remember` or the widget, Ask and Auto | 2,692 | 3,254 |
| An editor with `remember`, Plan | 1,789 | 2,351 |
| An editor with `remember`, Ask and Auto | 2,861 | 3,423 |
| The VS Code panel (`remember` and the widget), Plan | 2,462 | 3,023 |
| The VS Code panel, Ask and Auto | 3,534 | 4,096 |
| The terminal, every mode | unchanged | unchanged |

With a search key each is about 90 higher. `pnpm tsx scripts/roster-savings.ts` prints these.

## In the engine

- **The store.** `packages/engine/src/schedules.ts` keeps each workspace's tasks in `<app home>/schedules/<hash>.json`, keyed by the main checkout's real path (`rulesWorkspace`), never in the repository. A lane's session sees its main checkout's tasks. The file is read with a zod schema and written atomically.
- **The engine is the timer.** `Scheduler` lives in `engineShared`, one per engine process. It reads and writes each workspace's file one change at a time, and looks after every change and on a timer. Each look applies `planDue` to every task. A `run` starts a session through a connected editor and records it; a `miss` is recorded. The timer waits for the next occurrence, but at most a minute, because Node's timers count the monotonic clock, which stands still while the Mac sleeps. A run due during sleep starts within a minute of waking, by the grace rule.
- **No editor, no run.** A run starts through an editor connection, as a woken turn does (U49), because a turn needs one for its peer. While no editor is connected, a due task waits, and the grace rule decides once one connects. The engine exits 10 seconds after the last window leaves (U25), so in practice Geno runs a task while VS Code is open.
- **Restart.** Every look first ends a run that an engine that is gone left open, as `failed` with "Geno stopped before the run ended". The first connection watches its folder, so a run missed while the engine was off is caught up at once. The tasks and their runs are in the file, so nothing else needs taking up.
- **A run.** `startScheduled` in `serve.ts` makes a session in the main checkout, or a lane named from the title for an edit task, names it after the task, sets Plan or Auto, and runs the prompt in the background with `startBackground`, which Run in a new lane, Arena lanes and started suggestions now share (`startLaneSession` is a wrapper). The turn runs with the task's budget in place of the engine's limits. `runLimits` keeps that budget for the turns the run wakes, so a chain of wakes shares it, as U49's wakes share a prompt's. A prompt the user later types into the session starts afresh.
- **What a run is told.** `SCHEDULED_RUN_NOTE` follows the mode's system prompt: nobody reads the session until it ends and nobody can answer, so it ends with a short report, and in Plan it reports findings rather than a plan. A run gets no `ask_user` or `remember`, no editor actions and no `read_terminal`, since nobody is there and the editor should not move by itself at 9:00.
- **Its end.** When the run's turn ends, the scheduler reads the log with `runEndOf` and records the end and the cost. The session is a task like any other, so its end raises the usual notice through U25's trigger table: "Geno finished: …", or "Geno failed: …" for a run stopped at its budget.
- **Checkpoints.** Two tasks due at the same time start two sessions in one workspace at once. Both took their first checkpoint into the workspace's shared shadow repository together, and one failed with git's "File exists" on its `init`. `checkpoints.ts` now takes turns writing each shadow repository within the engine: a checkpoint, a restore and `changedSince` each hold it while they run. Any two sessions of one workspace could race the same way before.

## In the panel

- **The Scheduled section.** The Tasks pane gains a section after Done, with a count. Each row shows the title, a badge (Scheduled, Paused or Running), the schedule ("Weekdays at 09:00"), the next run ("Next Thu 8 Oct 09:00", "Paused" or "No run left"), how it runs and its budget ("Read-only · up to $0.05 and 20 model calls a run"), and the last run: "Last run Wed 7 Oct 09:00: Done · $0.01" with Open, which shows that run's session in the chat. A catch-up says "(late, for …)", a Run now "(Run now)", a missed run "Missed Tue 6 Oct 09:00: Geno was not running". The buttons are Run now (off while a run goes on), Pause or Resume, and Delete, which asks inline first, as a lane's Discard does. Under the section, a hint shows how to add one, and the empty pane's note says so too.
- **Where it lives.** `schedule-model.ts` turns a `ScheduleView` into a row, `schedule-view.ts` draws the section, and `schedule-wire.ts` checks the update at the boundary. `TaskHost` lists the tasks on connect, follows the updates, and sends the buttons. A run's own row in Needs you, Ready, Working or Done is the ordinary task row.
- **Width.** The title and the run line wrap. At 300px nothing leaves the pane and nothing scrolls sideways.

## Choices made in this unit

- The task file is the truth, and the runs live in it, not in session logs. A task outlives its sessions, and the list needs no log scan.
- The cursor `since` makes the rule one function of the file and the clock. A pause, a resume and a new schedule move it; Run now does not.
- One run per catch-up, whatever was missed. The user pays per call, and a review of main at 9:00 three days running is worth one run, not three.
- A run that is still going when its next comes due records the next as missed rather than queueing it.
- A read-only run is Plan, with a note that nobody reads a plan, rather than a new approval mode. Plan's rules already deny anything flagged without asking.
- An edit run is Auto in a lane, like a started suggestion, so it never touches the files the user works on.
- `/schedule` makes a task with no card, since the user typed it. Only the model's changes ask.
- The pre-approval is per chat and lasts while the engine runs, the narrowest one that saves a card per change.
- Times show in the panel's own zone, which is the engine's on the same Mac. The engine computes `nextAt` itself, so the two agree.

## Deferred

- A run starts only while an editor is connected to the engine, which in practice means while VS Code is open. A task due while VS Code is closed is caught up within the grace window once it opens.
- The Auto classifier's calls in an edit run are logged but not counted against the run's budget, as in any Auto turn.
- Two engines for the same folder, as during a settings change, each keep a timer on the same file. A due run is claimed by advancing `since` in one engine's write, but the two do not lock the file between them, so a run could start twice in that window.
- An edit task makes a lane per run, and lanes stay until applied or discarded. `gcode lane sweep` removes the clean ones.
- A read-only run's session shows Plan mode's "Start building" under its report.
- The panel has no form to make or edit a task; `/schedule` makes one, and the model's `update` changes one.
