# U59: dev server preview

The agent can start the project's dev server, check the running app, and stop the server again. The project names its dev servers in a launch file, in Claude Code's `.claude/launch.json` format. `preview_start` runs one as a background command (U45), waits until its port answers, and fetches the page once. The agent then opens the page with the browser tools (U29), takes a screenshot and reads the console errors. `preview_logs` reads the server's own errors, and `preview_stop` ends it. The panel shows the server as a live command step with Stop, and the Tasks pane lists it with Stop. The model is Claude Code's preview tools. The brief is the U59 row of "Harness ideas" in [plan-u19-on.md](plan-u19-on.md).

Before U59, a browser call to a local address where nothing listened said: "The bash sandbox has no network, so do not start a server there. Tell the user to run `pnpm dev` in their own terminal." U45 made localhost reachable from the sandbox, and that hint now points at `preview_start`.

## Data shape

`packages/core/src/preview.ts` names it. It holds only types and pure functions.

- **The launch entry.** `LaunchConfig` is `{ name, runtimeExecutable, runtimeArgs, port, url, cwd?, file }`, after the engine parsed it. `url` is the server's origin: the entry's `url`, or `http://localhost:<port>`. `cwd` is a workspace-relative folder. `file` is the launch file it came from.
- **The files.** `LAUNCH_FILES` is `.g-code/launch.json`, then `.claude/launch.json`. `mergeLaunchFiles` keeps the first entry of each name, so `.g-code` wins over `.claude`, and it lists the entry that lost as a problem. `LaunchConfigs` is `{ configs, files, problems }`. `files` is empty when the workspace has no launch file.
- **The URL rule.** `launchUrlOf(port, url?)` accepts only an http or https origin on this machine (`isLocalHost`, the browser's rule: `localhost`, `127.0.0.1`, `[::1]`, a name under `.localhost` or `.test`). Its port must be the entry's port, and it may have no path. Anything else leaves the entry out, with the reason.
- **The command line.** `commandLineOf(entry)` joins `runtimeExecutable` and `runtimeArgs`. It quotes only the words the shell would split or expand, so `pnpm dev` stays `pnpm dev` and the approval rules match it as they match the same line in bash.
- **The server's tag.** `PreviewTag` is `{ name, url }`. It rides on the background job (`BackgroundJob.preview`), its view (`JobView`), the Tasks record (`TaskJob`) and the end event (`background-end`), so the job reads as that dev server everywhere it shows, a replay included.
- **The server's state.** `PreviewStatus` is `starting` (the job runs, the port does not answer), `ready` (the job runs, the port answers) or `ended` (with the job's ended state). `previewStatusOf(jobState, answers)` derives it. The job's own state machine (U45) stays the one source of truth; readiness is probed, never stored.
- **The page check.** `PageCheck` is what one GET of the origin returned: `answered` with the status and the title or the redirect target, or `no-answer` with the reason.
- **What a start did.** `PreviewStart` is `started` or `reused` with the server, the seconds waited, the end of its output and the page check, or `taken`, when something this session did not start already answers on the port.
- **The log filter.** `filterLog(raw, { level, search, lines })` cleans terminal escapes with `cleanTerminalOutput`, redacts with `redactSecrets`, then keeps the matching lines. Level `error` keeps lines that mention an error, exception, failure, fatal, uncaught, unhandled, panic or Next.js's `⨯`. Level `warn` adds warnings, `⚠` and deprecations. `search` matches ignoring case. Because redaction runs first, a search cannot find a secret.
- **The texts.** `previewStartText`, `previewListText`, `previewLogsText`, `missingLaunchText`, `unknownLaunchText` and `notStartedText` are what the tools return.

| Constant | Value | What it bounds |
| --- | --- | --- |
| `PREVIEW_READY_TIMEOUT_S` | 60 | How long `preview_start` waits for the port |
| `PREVIEW_PAGE_TIMEOUT_S` | 30 | How long the first GET may take; a dev server compiles the page on it |
| `PREVIEW_LOG_LINES` | 50, at most 500 | Lines `preview_logs` returns |
| `PAGE_TITLE_MAX` | 120 | Characters of the page title kept |

## The tools

| Tool | Input | Does |
| --- | --- | --- |
| `preview_start` | `{ name? }` | Reads the launch files, picks the entry (`name` may be left out when there is one), reuses a running server of that name, or starts it. Waits for the port, then GETs the origin once. |
| `preview_list` | `{}` | The launch entries, the entries left out and why, and the servers this session started with their state. |
| `preview_logs` | `{ name?, level?, search?, lines? }` | The server's stdout and stderr, filtered and redacted. `name` may be left out when the session started one. |
| `preview_stop` | `{ name }` | Stops a server this session started: SIGTERM, then SIGKILL after 3 s. |

- **A ready start.** "Started dev server "web" (`pnpm dev`) as bg-1. It answers at http://localhost:3000. GET http://localhost:3000/ returned 200, titled "Payload". To see it, open http://localhost:3000 with the browser tool mcp__browser__new_page, then mcp__browser__take_screenshot, and mcp__browser__list_console_messages for the page's console errors; load them with tool_search first. preview_logs with { "name": "web", "level": "error" } reads the server's own errors." A 500 adds that the server failed on the page and to read its errors. A redirect is reported, never followed, since it may lead off this machine.
- **A slow start.** After 60 s with no answer, the result says the server may still be compiling, gives the end of its output, and says to read `preview_logs` or call `preview_start` again to wait longer. The server keeps running.
- **A start that dies.** "It exited with code 1 before it answered at …", with the end of its output.
- **Reuse.** A second `preview_start` of a name that runs in this session waits for its port and reports it again. Nothing new starts.
- **A taken port.** When something answers on the port and this session did not start it, nothing starts. The result says it may be the user's own dev server or one another chat started, and to open the URL as it is or ask the user to free the port. Without this check, Next.js would move to port 3001 and the URL would be wrong.
- **No launch file.** `preview_start` fails with the format and an entry built from package.json's dev script (`devServerCommand`, which U29 added for the old hint), such as `{ "name": "dev", "runtimeExecutable": "pnpm", "runtimeArgs": ["dev"], "port": 3000 }`. The model writes the file with `edit` under the usual approval, then calls `preview_start` again.
- **Refusals.** An unknown entry name lists the names there are. `preview_logs` or `preview_stop` of a server this session did not start says Geno stops and reads only the servers it started, and names the ones it did.

### Approval and the sandbox

- Starting a server is a command. `preview_start` sends the entry's command line through the same lane check, rules, remembered rules, classifier and approval card as a `bash` call with `run_in_background`. `pnpm dev` runs without a question in Ask, goes to the classifier in Auto, and `curl …` as an entry is refused in a non-interactive run, as in bash.
- The command runs in the sandbox, with the workspace (or the entry's `cwd`) as its folder and `PORT` set to the entry's port, which Next.js and most dev servers read. U45 set `allowLocalBinding` on the sandbox, so the server may listen on loopback. On macOS the engine and Chrome, which run outside the sandbox, reach it. On Linux they do not (see Deferred).
- The engine probes the port with a TCP connect from its own process, trying every address the host resolves to, so a server on `127.0.0.1` answers at `localhost`. The one GET runs from the engine too, with no redirect followed and a local https certificate not checked.
- `preview_list` and `preview_logs` only read. They run beside other calls and ask nobody, in every mode.
- `preview_stop` finds only this session's jobs. A server another session started, or the user's own, is never stopped.

### Modes and the roster

- Plan offers `preview_list` and `preview_logs` and leaves out `preview_start` and `preview_stop`, as it leaves out `bash_output` and `bash_stop`. A session that switched to Plan with a server running can still read it.
- A subagent gets none of the four (`CHILD_LEAVES_OUT`), because it ends with its call and starts no background command.
- All four are deferred behind `tool_search` (U46). They add about 485 tokens to what deferring saves in Ask, Auto and non-interactive runs, and about 255 in Plan, in every client:

## The engine

- `packages/engine/src/preview.ts` is the boundary. `parseLaunchFile` parses one file with zod, entry by entry, so one bad entry leaves the others usable and is listed with its zod issue. `readLaunchConfigs` reads both files and merges them. `answers(url)` is the TCP probe, `untilAnswers` polls it every 250 ms until the port answers, the job ends, the time is up or the call is cancelled, and `checkPage` is the one GET, reading at most 64 KiB for the title.
- `packages/engine/src/tools/preview.ts` holds the four executors. They get the session's `BackgroundJobs`, and a `StartServer` callback from `agentExecutors`, which runs the command line through `approveCommand` and `startInBackground`, as `monitor` does.
- `BackgroundJobs` gains `jobs(sessionId)` (newest first) and `kept(sessionId, id)` (all the output the job keeps, and its end). `start` takes the tag, a folder and an env.
- A server's step and its Tasks row come from the jobs' `changed` hook, as for any background command.

### Wakes

A dev server does not wake its session (U49). `Wakes.waitsFor` leaves running servers out, and `triggerOf` gives a server's `background-end` no trigger. A server is meant to run on. If it waked the session, the Tasks pane would show the chat as "Waiting to wake" for as long as the server ran, and a crash would start a paid turn by itself. Its end still reaches the model, at the next request, as every background end does.

## In the panel

- **The step.** A `preview_start` call whose job started draws as a command step (`render.ts`): the title "Dev server web", the command line in the IN box, the server's live output in the OUT box, newest lines last, and under it "Serving http://localhost:3000 as bg-1" with Stop. Once it ends the row says how ("bg-1 was stopped by the user"). A `preview_start` that started nothing, such as one without a launch file, stays an ordinary step. The job's view now carries its command line and tag (`BackgroundStep.command` and `.preview`), and a replayed end carries the tag too.
- **The verbs.** Once done, the four tools read "Started the dev server", "Listed the dev servers", "Read the dev server logs" and "Stopped the dev server" on the rail.
- **Tasks.** Every running background command under a task now has Stop, which sends `_gcode/backgroundStop`, the step's Stop. A dev server reads "web on localhost:3000", short enough to keep the port in view at 300px. A server leaves the row once it ends.

## Choices made in this unit

| Choice | Taken | Not taken, and why |
| --- | --- | --- |
| Where the tools live | Agent tools beside `bash`, since they need its approval and the session's jobs | Editor-only tools: a terminal run starts dev servers as well |
| How a server is kept | A background job with a tag | A registry of its own, which would have to agree with the job's state |
| Seeing the page | The browser tools the session already has, opened at the URL `preview_start` returns | A `preview_screenshot` tool of its own: a second path to the same Chrome, with its own approval rules |
| Readiness | A TCP probe, then one GET for the status and title | Only a GET: Next.js compiles on the first request, which would hold every poll |
| A taken port | Start nothing and say so | Start anyway: Next.js would move to another port and the URL would be wrong |
| `PORT` | Set to the entry's port | Leave it: `next dev` would ignore an entry's port without a flag |
| Wakes | A server does not wake its session | Wake on its end: the session would wait forever, and a crash would start a paid turn |
| Stop in Tasks | On every background command | Only on dev servers: the job and the Stop are the same for both |

## Deferred

- On Linux, bubblewrap gives each command its own network namespace, so neither the engine nor Chrome reaches a server the sandbox started. There `preview_start` waits 60 s and reports the server as still starting. The engine e2e's server tests and the integration test run on macOS only.
- The browser is off by default, and only the user turns it on in the MCP pane. Without it the agent has `preview_start`'s page check and `preview_logs`, not a screenshot or the console.
- Dev servers count toward the 4 background commands a session may run at once, shared with `bash`.
- Servers die with their engine, as every background command does (U45). An engine killed with SIGKILL leaves them running.
- A server the model stopped logs no end event, so after a reload its step shows only the call (U45).
- An entry takes no `env` of its own; the command gets the session's environment and `PORT`.
- `preview_start` cannot tell which other chat holds a taken port; it says only that this session did not start it.
