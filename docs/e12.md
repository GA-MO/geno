# E12 and E13: the wire protocol and buffer conflicts

Phase 5 put a chat panel in VS Code over the engine running as a child process. This page records the protocol decision (E12) and how edits to files with unsaved changes behave (E13).

## E12: ACP, with one extension method

**Decision.** The engine and the extension speak the Agent Client Protocol (ACP) v1 through its official TypeScript SDK, `@agentclientprotocol/sdk` 1.7.0 (repository `github.com/agentclientprotocol/typescript-sdk`). Both sides use the SDK's types and its parsed handlers. The engine side is `gcode serve --stdio` (`packages/engine/src/serve.ts`); the client side is the extension (`packages/extension/src/chat/`).

The synthesis set the rule as "adopt ACP if 2 or fewer custom methods are needed." Phase 5 needed one custom method, `_gcode/diagnostics`, plus one `_meta` key and one error code. ACP carries everything else.

`serve` is an adapter, not a second loop. Each `session/prompt` reopens the session log with `resumeSession` and calls `runAgent`, the function behind `gcode agent`. Sessions, tools, the sandbox, checkpoints and the log are the same code. What differs is the surface that `drive` is given. The terminal surface reads and writes the disk and prints, and the editor surface reads and writes through ACP and sends session updates.

### Flows mapped to messages

| Flow | Direction | ACP message |
| --- | --- | --- |
| Start the engine | extension spawns `node <engine>/dist/cli.js serve --stdio` | `initialize` with `clientCapabilities.fs.readTextFile` and `writeTextFile` true, and `_meta["gcode/diagnostics"]: true` |
| Start a conversation | extension to engine | `session/new` with the workspace folder as `cwd`. The ACP session id is the engine's session id, and the engine's stderr names the log file. |
| Send a message | extension to engine | `session/prompt` with text blocks. The response's `stopReason` ends the turn. |
| Streamed assistant text | engine to extension | `session/update` `agent_message_chunk` |
| Tool call starts | engine to extension | `session/update` `tool_call`: id is the model's tool-use id, title is the CLI's one-line form (`edit math.ts`), kind from a table (read, search, edit, execute), status `in_progress` |
| Tool call ends | engine to extension | `session/update` `tool_call_update`: status `completed` or `failed`, with the result text |
| Stop button | extension to engine | `session/cancel`. The turn's abort signal fires and the prompt answers `cancelled`. Open permission prompts are answered `cancelled`, as ACP requires. |
| Read a file (buffer bridge) | engine to extension | `fs/read_text_file`. The extension answers with the open document's text, unsaved edits included, or the disk text. A missing file is `RequestError.resourceNotFound` (-32002), which the engine reads as "no such file". |
| Write a file (buffer bridge) | engine to extension | `fs/write_text_file` with `_meta["gcode/baseHash"]`, the sha256 of the text the edit was computed from (null for a new file). An open document gets a `WorkspaceEdit`, so undo works and the disk changes on save. A closed file is written to disk. |
| Write against a changed file | extension to engine | JSON-RPC error -32010 with `data.reason: "stale-base"`. The engine turns it into the Phase 3 `stale-base` failure. |
| Approval for a denied command | engine to extension | `session/request_permission` on the running tool call, with options `allow_once` and `reject_once`. The panel shows them as buttons. |
| Editor diagnostics | engine to extension | `_gcode/diagnostics` `{ sessionId, paths }` returns `{ diagnostics: [{ path, line, character, severity, message, source }] }`, with lines and columns counted from 1. |
| Errors (transport, refusal, limits) | engine to extension | `agent_message_chunk` text `[kind] message`. ACP's `notice` update is marked unstable and needs a client capability, and the spec says to fall back to agent text. |

### What ACP could not express

- **Diagnostics.** ACP has no client method for them, so `_gcode/diagnostics` is an extension method under the underscore convention. The engine calls it only when the client set `_meta["gcode/diagnostics"]` at `initialize`. The `check` tool uses it when the workspace has no check command.
- **A conditional write.** `fs/write_text_file` has no precondition. The base hash rides in `_meta`, and a refusal uses an error code of our own (-32010) in the JSON-RPC server range. A client that ignores the key still works, but without the write-time check. The engine's own check before the write still runs.
- **A budget stop.** ACP's stop reasons have no budget limit. `--max-cost` maps to `max_turn_requests`, and the logged error event says which limit it was.
- **Not needed yet.** Checkpoint restore and per-hunk keep and undo are Phase 6. The synthesis expected both to need extension methods, which would bring the count to three. Revisit the decision then. The second half of the E12 method, pointing Zed at the engine, was not run.

## E13: buffer and disk conflicts

**Rule.** The engine reads through the buffer bridge and edits against what it read. A write fails as `stale-base`, and the model is told to read the file again, when the file changed since the read. Two checks enforce it:

1. Before writing, the edit tool reads the current text (through the bridge) and compares its hash to what the model last read. A user's keystroke between the model's `read` and its `edit` fails here.
2. The write carries the hash of the text the edit was computed from. The extension compares it to the buffer before applying. A keystroke that lands while the edit is being resolved fails here. If `applyEdit` returns false, the write also fails as `stale-base`. That covers a keystroke still in flight from the renderer, assuming VS Code checks the document version on a `WorkspaceEdit` (inferred from its source layout, not tested here).

The read tool records the exact text it showed the model as the base, not a second read after it, so a change right after the read makes the next edit stale rather than letting it pass.

**Measured.**
- The integration test (`packages/extension/test/chat.integration.test.ts`) types an unsaved line, then runs a turn with a fake model that reads and edits it. The read result held the unsaved line. The edit landed in the buffer, undo and redo worked, and the disk kept its old text until save. In a second turn the fake model's edit is held until the suite types into the buffer. The edit failed with `math.ts changed since it was last read; read it again before editing`, nothing was written, and the typed text survived. Lost keystrokes: 0. Lost agent edits: 0.
- The engine test (`packages/engine/test/serve.e2e.test.ts`) covers the write-time refusal (check 2) with an ACP client that rejects the write. `packages/engine/test/files.test.ts` covers the same race on disk.
- Live smoke on Model Studio `qwen3.8-flash` (`pnpm tsx packages/extension/test/chat-smoke.ts`): the model's `grep` found no `unsaved` on disk, its `read` returned the unsaved line from the buffer, and its edit landed in the buffer with the disk untouched. 5 model calls, an estimated $0.0023.

**Gaps.** `grep`, `glob` and `list` search the disk, so they do not see unsaved text; `read` does. Checkpoints snapshot the disk, so a rewind does not restore unsaved buffer text. Untitled documents have no path and are not reachable through the bridge. Diagnostics are read when the model calls `check`, not right after an edit, because a language server reports on an edited buffer some time later and an immediate read would show stale results.
