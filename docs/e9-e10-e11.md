# E9, E10 and E11: next-edit prediction with Zeta 2.1

Phase 8 built next-edit prediction: an edit-history tracker, a Zeta 2.1 prompt builder and parser, a replay harness, and inline edits through VS Code's proposed API. This page reports what it measured on the Apple M4 with 16 GB of RAM. The model, prompt and server are described in `docs/tab-model.md`.

**Verdict.** Zeta 2.1 at Q4_K_M under llama.cpp misses the latency bar on this Mac by a factor of about 45. Total latency is 9.4 s at p50 and 19.0 s at p90, against a bar of 200 ms and 500 ms. Per the exit rule, next-edit is off by default (`gcode.tab.nextEdit` is `false`) and FIM stays the shipped Tab. The code, the harness and the Insiders integration stay in place behind the setting.

Every number below comes from a file in `docs/results/`. Each run has a `.txt` file, which is the printed summary of `gcode tab replay`, and a `.jsonl` file with one row per moment. The tables were made with `node scripts/next-edit-summary.mjs docs/results/<run>.jsonl`.

## How the runs were made

- **Moments.** No recorded editing sessions exist yet, so edit moments come from git history as a proxy. Each of the 47 apply triples in `~/.g-code/evals/apply/` is one commit's change to one file, from `next-15-template` (25 triples) and `payload-site-template` (22). For a change with k+1 hunks, the moment replays the first k hunks on the parent file as the edit history and makes hunk k+1 the target. The cursor sits at the end of hunk k. Hunks are taken in file order, which is not necessarily the order a person typed them. The triples yield 69 moments, under the 100 the brief allowed, and all 69 were used.
- **Prompts.** These are the extension's own prompts, built by `buildNextEditPrompt` with the default budget (350-token editable region, 150 tokens of context, 4096 in all). They carry no related files, because the triples hold only the changed file.
- **Grades.** A prediction is *exact* when applying it leaves the file as the target hunk does. It is *region* when it changes text overlapping the target hunk but differently, *wrong-location* when it changes something else, and *none* when Zeta answers "no edit".
- **Serving.** `scripts/next-edit-replay.sh` starts a fresh `llama-server` for every run (llama.cpp build 11146), because its RAM prompt cache would otherwise serve earlier runs' prompts. Each run sends 3 uncounted warmup requests built from synthetic Python unlike the corpus, then the 69 moments one at a time. Within a run, consecutive moments from the same file share a prompt prefix, which the server reuses. The tables report processed tokens separately for that reason.
- **Machine.** The GPU is shared with the desktop and with other agents' work. The 1-minute load average ranged from 0.8 to 8.4 across the runs (each `.txt` file prints it at start and end).

## E9: serving latency

Three runs at history N = 6, each on a fresh server. The first is the E10 run at N = 6.

| Run | TTFT p50 / p90 (ms) | Total p50 / p90 (ms) | Prompt tokens p50 / p90 | Generated tokens p50 / p90 | Server generation p50 / p90 (ms) |
| --- | --- | --- | --- | --- | --- |
| `e10-h6` | 6867 / 13707 | 8881 / 19019 | 788 / 1458 | 14 / 134 | 839 / 11414 |
| `e9-h6-run2` | 7260 / 14411 | 9374 / 18720 | 788 / 1458 | 14 / 134 | 856 / 10709 |
| `e9-h6-run3` | 7665 / 14464 | 9555 / 20877 | 788 / 1458 | 14 / 134 | 979 / 11400 |
| Median (range) | 7260 (6867 to 7665) / 14411 (13707 to 14464) | 9374 (8881 to 9555) / 19019 (18720 to 20877) | 788 / 1458 | 14 / 134 | 856 / 11400 |

Against the bar of 200 ms at p50 and 500 ms at p90, both time to first token and total latency miss at every percentile in every run. The three runs returned identical text for all 69 moments, so they measured the same work.

**What limits it.**

- **Time to first token is prompt processing.** The server's prompt-eval time accounts for all but 18 ms of time to first token at the median (`e10-h6`, `ttftMs` against `promptMs`). Processing ran at a median 10.2 ms for each uncached token, about 100 tokens a second. The 3,000-token card sample processed faster, at 160 tokens a second, because small batches cost more per token, as Phase 7 also found with Qwen.
- **Total latency is generation on top of that.** Zeta answers "no edit" with 14 tokens (`<|marker_N|><|marker_N|>`), which took a median 826 ms of generation alone. When it predicts an edit, it rewrites every line from one marker to the next, between 48 and 223 tokens in `e10-h6`. Those 19 predictions took 4.9 s to 37 s in all. Generation ran at about 13 to 20 tokens a second. An 8B model at Q4_K_M reads about 4.7 GB of weights per token, and the M4's memory bandwidth of 120 GB/s (Apple's figure) caps that at roughly 25 tokens a second, so generation runs near its ceiling.
- **The arithmetic rules out tuning to the bar.** With the whole prompt cached, a "no edit" reply alone takes about 0.8 s, four times the p50 bar. An edit cannot come in under 500 ms unless the reply is under about 8 tokens.
- **Speculative decoding helps but not enough.** The `e9-h6-ngram` run used prompt n-gram speculation (`--spec-type ngram-simple --spec-draft-n-max 16`). It returned the same 69 replies and cut generation p90 from about 11 s to 5.2 s, giving a total p90 of 15.2 s. Its total p50 was 9.2 s, because most replies are 14 tokens, which speculation cannot shorten much.

| Run | TTFT p50 / p90 (ms) | Total p50 / p90 (ms) | Server generation p50 / p90 (ms) |
| --- | --- | --- | --- |
| `e9-h6-ngram` | 7216 / 14241 | 9208 / 15183 | 854 / 5183 |

**Errors and completeness.** Every run finished all 69 moments. The command fails outright on a server error. No reply was malformed, and every reply carried server timings.

**What would reach the bar.** This part is inference, not measurement. Cold prompts of about 800 tokens need prefill near 8,000 tokens a second to fit in 100 ms, and a 100-token rewrite in 400 ms needs about 250 tokens a second of generation. A data-centre GPU running vLLM, such as an H100 or L40S, with FP8 weights and n-gram or draft-model speculation, is the kind of hardware that serves an 8B model at those rates. Network round trips would add tens of milliseconds. A faster Mac does not close the gap. An M4 Max has about 4.5 times the memory bandwidth, which would bring a 14-token reply near 200 ms but leave a 100-token rewrite above 1 s. Renting a GPU was not tried, and this page gives no price, because none was measured.

## E10: quality and history size

| Run | Moments | exact | region | wrong-location | none |
| --- | --- | --- | --- | --- | --- |
| `e10-h1` (N = 1) | 69 | 3 | 5 | 7 | 54 |
| `e10-h3` (N = 3) | 69 | 4 | 7 | 8 | 50 |
| `e10-h6` (N = 6) | 69 | 3 | 7 | 9 | 50 |

- Zeta predicted the next hunk exactly in 3 or 4 of 69 moments, and found its location (exact or region) in 8 to 11. It answered "no edit" in 50 to 54.
- History size barely matters on this set, because few moments have much history. At N = 6, 28 moments have one earlier hunk, 16 have two, and only 25 have three or more (`historyEntries` in `e10-h6.jsonl`). Going from N = 1 to N = 3 changed 8 replies. It turned 5 "no edit" answers into predictions and 1 prediction into "no edit". Going from 3 to 6 changed 2. With 69 moments, these differences are within what one or two moments can swing. They do not support choosing an N, and 6, Zed's own cap, stays the default.
- 62 of 69 targets lie inside the editable region the model may rewrite. The other 7 are out of reach by construction.
- The proxy is hard. Many targets are dependency version bumps in `package.json` and new lines in documentation, which the earlier hunks do not imply. Real editing sessions, where the next edit follows from the last one, as in a rename, should score higher. That is a guess until the live trial records them.

The synthesis planned grading with plain-English assertions judged by a larger model, as Zed did. This harness grades mechanically instead, so the counts are strict. A prediction that is right in substance but differs in whitespace counts as region, not exact.

## E11: proposed API stability

The extension uses `inlineCompletionsAdditions` (`isInlineEdit`, `displayLocation`, `handleEndOfLifetime`). Its `.d.ts` is copied from microsoft/vscode at commit `429a4ec703266abbd31f6886764e4127955bdc9d`, which is the commit of the VS Code Insiders build `1.141.0-insider` that `@vscode/test-electron` downloaded on 2026-10-05.

The integration test (`packages/extension/test/tab.integration.test.ts`) runs the extension in that Insiders build with `--enable-proposed-api g-code.g-code`, against a fake Zeta server. The test makes two edits that rename `total` to `sumOf` on line 1. It then checks three things. The first next-edit shown is the matching call on line 7, away from the cursor. Accepting it changes exactly that call. The accept is logged. With `isInlineEdit` turned off, the same test fails, so it does exercise the inline-edit path. The Phase 7 test in the same file still passes on stable VS Code 1.140.0. There, VS Code strips the proposal from an extension in development mode (per its source, `extensionsProposedApi.ts`), and the extension registers only the FIM provider.

E11's real measurement is four weeks of Insiders updates with the smoke test run daily, and it has not started. To run it, let Insiders update, run `pnpm vitest run packages/extension` each day, and note the date of any break and the hours to fix it. When the `.d.ts` changes, copy it from the commit of the new build (`product.json` in `.vscode-test/vscode-darwin-arm64-insiders` names the commit). The extension detects the proposal through `vscode.languages.inlineCompletionsUnificationState`, which the proposal marks "temporary: to be removed". If that getter goes, next-edit silently falls back to FIM, and the smoke test catches it.

## The live trial

The two-week trial is yours to run, and it only makes sense with next-edit turned on and its latency accepted for the trial.

1. Start both servers: `scripts/tab-server.sh` for FIM on 8012 and `scripts/next-edit-server.sh` for Zeta on 8013.
2. Use VS Code Insiders with the extension in development mode, or pass `--enable-proposed-api g-code.g-code`. Stable VS Code ignores next-edit.
3. Turn `gcode.tab.nextEdit` on for the next-edit days and off for the FIM days. The setting takes effect on the next request, with no reload. Alternate whole days, so both see the same kind of work.
4. Every request goes to `~/.g-code/tab-events.jsonl`. Next-edit requests are `kind: "next-edit"` records. Each holds the editable region, the history the model saw, and the predicted edit (`edit`), in addition to the Phase 7 fields. VS Code reports accepts through the item's command and rejections through `handleEndOfLifetime`, so next-edit outcomes are more exact than FIM's inferred ones.

Read the trial with `pnpm gcode tab report --since <first day of the trial>`. It prints one block per kind and model, for example `model: zeta-2.1.Q4_K_M (next-edit)` and `model: qwen2.5-coder-1.5b-q8_0 (fim)`. Compare these lines between the two blocks:

- `accept per shown` is the main measure. E10 asks whether next-edit beats FIM on it.
- `shown` divided by the hours each mode was on gives suggestions per hour. If next-edit shows too often, add a suppression threshold.
- `cancelled` counts requests overtaken by typing. Expect it to be high for next-edit at these latencies, because most predictions arrive after you have moved on. Next-edit marks a reply that arrives after the document changed as `suppressed: stale`.
- `total latency` p50 and p90 should match E9 if the setup matches.
- `persisted per accepted` shows whether accepted edits survive five minutes.
