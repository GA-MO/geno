**AI model ที่ Geno ใช้คือ API ที่ไม่มีความจำ** Geno ส่ง request หนึ่งก้อนไป model ส่งคำตอบหนึ่งก้อนกลับมา แล้วจบ
model ไม่รู้ว่าเคยคุยอะไรกับคุณมาก่อน ไม่รู้ว่าอยู่ในเครื่องไหน และไม่เคยรันคำสั่งเองแม้แต่ครั้งเดียว

ทุกอย่างที่ทำให้ Geno ดูเหมือน "เอเจนต์ที่ทำงานต่อเนื่อง" อยู่นอก model:
การจำบทสนทนา การรัน tool การขออนุญาต การวาดหน้าจอ และการตัดสินว่าจะเรียก model อีกรอบหรือไม่
ส่วนที่ทำงานเหล่านี้เรียกว่า **harness** ใน Geno คือ Geno engine

สองคำที่ใช้ตลอดบทนี้

- **tool** คือความสามารถที่ Geno เปิดให้ model ขอใช้ เช่น `read` อ่านไฟล์ `list` แสดงรายการไฟล์ และ `bash` รันคำสั่ง
  model รัน tool เองไม่ได้ มันเขียนคำขอเป็น JSON ในคำตอบ แล้ว Geno เป็นคนรันและส่งผลกลับ
- **turn** คือทุกอย่างตั้งแต่คุณส่ง prompt หนึ่งข้อจนคำตอบจบ turn หนึ่งเรียก model ได้หลายครั้ง

คำอื่นที่เจอในบทนี้มีคำอธิบายสั้นใน[คำศัพท์](/start/glossary/)

## ดูของจริง: request ที่ 1 กับ request ที่ 2

การ์ด JSON ในบทนี้คัดจากการรันจริง แต่ละรายการ (เช่น A06) คืองานทดสอบหนึ่งงานที่รัน Geno กับ model qwen3.8-flash แล้วเก็บไฟล์ไว้

ในการรันจริงรายการ A06 ผู้ใช้ถามว่า "Show me what the package.json scripts are, list the files under src, and tell me which test files exist."
turn นี้เรียก model สองครั้ง

ก่อนดูการ์ด รู้จักโครงของ request สามอย่าง

- request เป็น JSON ก้อนหนึ่ง บทสนทนาอยู่ใน field `messages` ซึ่งเป็นรายการข้อความเรียงตามเวลา
- แต่ละข้อความมี `role` ได้แค่สองค่า: `user` คือฝั่งที่ส่งมาหา model (คุณและ Geno) และ `assistant` คือคำตอบของ model
- เนื้อหาของข้อความอยู่ใน `content` ซึ่งเป็นรายการ**บล็อก** แต่ละบล็อกมี `type` บอกชนิด
  เช่น `text` (ข้อความ) `tool_use` (คำขอเรียก tool ของ model) และ `tool_result` (ผลของ tool ที่ Geno ส่งกลับ)

**ครั้งที่ 1** `messages` มีข้อความเดียวจากฝั่ง user ข้างในมีสี่บล็อก บล็อกสุดท้ายคือคำถามของผู้ใช้
สามบล็อกแรกเป็นสิ่งที่ Geno ใส่ให้: ไฟล์คำสั่งของผู้ใช้ สภาพแวดล้อมของเครื่อง และข้อความจาก hook
(คำสั่งที่ผู้ใช้ตั้งให้ Geno รันเมื่อเกิดเหตุการณ์ เช่น ตอนส่ง prompt) อธิบายใน[Model รู้ได้อย่างไรว่าต้องทำอะไร](/foundations/how-the-model-knows/)

model ตอบว่าจะดูไฟล์ก่อน แล้วขอเรียก tool สามตัว: `read` `list` และ `glob`
Geno รันทั้งสามบนเครื่องของคุณ แล้วเรียก model **ครั้งที่ 2**

<Payload of={frontmatter.payloads.second} />

สังเกตสามข้อความใน `messages`

1. ข้อความแรกคือข้อความเดิมทั้งก้อน ทั้งคำถามและสามบล็อกที่ Geno ใส่ (พับไว้ คลิกเพื่อเปิด)
2. ข้อความที่สองคือคำตอบของ model จาก request ที่ 1 ซึ่ง Geno คัดลอกกลับไปให้ทุกไบต์ รวมถึงคำขอ tool ทั้งสาม
3. ข้อความที่สามคือผลของ tool ทั้งสาม ในลำดับเดียวกับที่ model ขอ
   ข้อความนี้มี `role` เป็น `user` เพราะ API มีแค่สองฝ่าย ทุกอย่างที่ไม่ใช่คำตอบของ model จึงเป็นฝั่ง `user`
   ผลแต่ละอันเป็นบล็อก `tool_result` ที่มี `tool_use_id` ชี้ไปยัง id ของคำขอที่มันตอบ
   (ดู[ผลของ tool ส่งกลับอย่างไร](/foundations/tool-results/))

model ไม่ได้ "จำ" ว่าเคยขออ่าน `package.json` Geno เล่าให้ฟังใหม่ทั้งหมดใน request นี้
ถ้า Geno ไม่ส่งข้อความที่สอง model จะไม่รู้เลยว่าตัวเองเคยตอบอะไร

การ์ดสองใบนี้มาจาก `requests.jsonl` ซึ่ง engine สร้างใหม่จาก session log (บันทึกของบทสนทนา อธิบายในหัวข้อถัดไป) ตอนเก็บผล ไม่ใช่ไบต์ที่ส่งจริง
ไบต์ที่ส่งจริงอยู่ใน wire log (`wire.jsonl`) ซึ่งบันทึกทุก request และ stream ตามที่วิ่งบนสาย
นี่คือ wire log ของรายการเดียวกันที่รันซ้ำ: request ที่สองก็มี `messages` สามข้อความแบบเดียวกัน

## ทำไมต้องส่งทั้งหมดทุกครั้ง

API ของ model แบบนี้ไม่มี session ฝั่ง server ที่ Geno ไปต่อได้
ผู้ให้บริการรับ request คำนวณคำตอบ แล้วลืม ถ้าอยากให้ model เห็นบทสนทนา ต้องส่งบทสนทนาไปทั้งหมด

Geno จึงเก็บความจริงไว้ที่เดียว คือ **session log** ไฟล์ JSONL (JSON หนึ่งก้อนต่อบรรทัด) ที่มี event เรียงกัน
(`user` `assistant` `tool-result` `notice` และอื่นๆ) ก่อนเรียก model ทุกครั้ง
`buildRequest` ใน `packages/core/src/request.ts` สร้าง request ใหม่จาก log ทั้งก้อน
ส่วนที่แปลง event เป็น `messages` คือ `replayMessages` ใน `packages/core/src/session.ts`

ผลที่ตามมามีสองข้อ

- **request เป็นผลของ log เสมอ** Geno จึงสร้าง request ในอดีตขึ้นมาใหม่ได้ทุกไบต์ ด้วยคำสั่ง `gcode session request <session-id> <turn>`
  (engine เก็บส่วนที่ไม่ใช่ `messages` ไว้ครั้งเดียวต่อ hash ใน `packages/engine/src/snapshots.ts`)
- **request โตขึ้นทุกรอบ** ยิ่ง turn ยาว ยิ่งส่งมาก Geno ลดต้นทุนด้วย prompt cache (ผู้ให้บริการจำส่วนต้นที่ซ้ำกับ request ก่อน จึงคิดเงินส่วนนั้นถูกลง)
  และย่อบทสนทนาด้วย compaction (ให้ model สรุปส่วนเก่าแทนการส่งทั้งหมด) ดู[Memory และ context window](/foundations/memory-and-context/)

## แบ่งงานกันอย่างไร

| model ทำ | harness (Geno) ทำ |
| --- | --- |
| อ่าน request แล้วเขียนคำตอบ | เก็บบทสนทนาใน session log และสร้าง request ใหม่ทุกครั้ง |
| เขียนข้อความถึงคุณ | stream ข้อความนั้นไปที่แผงแชตและวาดเป็น Markdown |
| เขียนคำขอเรียก tool เป็น JSON | ตรวจ input ตรวจสิทธิ์ รัน tool บนเครื่องของคุณ แล้วส่งผลกลับ |
| บอกว่าจบหรือยังผ่าน `stop_reason` (field ท้ายคำตอบที่บอกเหตุผลที่หยุด) | ตัดสินว่าจะเรียก model อีกรอบ จบ turn หรือหยุดเพราะเกินงบ |
| (ไม่มี) | ถามคุณก่อนรันคำสั่งเสี่ยง บังคับ sandbox (กรอบที่ให้คำสั่งเขียนได้แค่ในโฟลเดอร์งานกับโฟลเดอร์ชั่วคราว) จับเวลา และ retry เมื่อเครือข่ายล่ม |

คอลัมน์ขวายาวกว่าซ้ายมาก นั่นคือเหตุผลที่บทนี้ทั้งบทพูดถึง harness
